# Triage

- [TASK] `wrapHandler` cannot observe attempt failures — the middleware chain wraps `runJobAttempt` (the executor), which catches handler/callback errors, reschedules, and returns normally, so a `catch` around `next()` never runs (only `finally` does). `wrapPrepare`/`wrapExecute`/`wrapComplete` do see errors, since they wrap the user callback directly — an undocumented asymmetry. Decide between documenting the current behavior, adding an `onAttemptError` hook, or moving the chain inward to wrap the handler. Any change that makes `catch` live is breaking (dead catch blocks become live, double-reporting against `jobAttemptFailed`). See `design/wrap-handler-error-visibility.md`.

# Short term

- [TASK] Reads by deduplication — `getChain`/`getChains` resolve the single chain `createChain` would dedup onto (newest in scope) by `DeduplicationOptions`, not only `id`/`ids`. Required `typeName` scopes the match per chain type (mirrors `createChain`); composes with `lock`. Core `StateAdapter` + adapters. Prereq for built-in cleanup. See `design/reads-by-deduplication.md`.
- [TASK] Built-in cleanup — `createCleanupJobTypes()`, policy-free `createCleanupProcessors()`, and `scheduleCleanup`/`unscheduleCleanup` (per-name recurring schedules, CAS upsert, `typeNames` scoping) from a `queuert/cleanup` subpath. Depends on the two reads tasks above. See `design/builtin-cleanup.md`.
- [TASK] Expose deduplication key to the dashboard — the dedup key is persisted on the `StateJob` row (and adapter tables) but `mapStateJobToJob` drops it, so it never reaches the public `Job` entity or any dashboard route. Add it to the public job entity (and dashboard job detail) so users can see which key a job deduped onto.
- [BUG] Surface caller-supplied job ID collisions as a typed `DuplicateJobIdError` at the state-adapter boundary — `id` assigns identity and must not act as a deduplication handle. Today a colliding `id` on `createChain` / `createChains` does not error at all: the SQL adapters' root-insert `ON CONFLICT (chain_id, chain_index) DO UPDATE` silently returns the **existing** row (caller's `typeName`/`input`/`schedule` dropped) with `deduplicated: false`, while the in-process adapter overwrites the existing root in place; intra-batch duplicates diverge again across all three. Detect and throw from JS rather than letting the constraint fire, so a PG `23505` doesn't abort the caller's transaction. See `design/caller-supplied-id-collisions.md`.
- [BUG] Deduplication is not atomic on PostgreSQL ([#3](https://github.com/kvet/queuert/issues/3)) — `createChains` decides dedup with a plain `SELECT` and inserts the misses in the same statement, so under READ COMMITTED two concurrent same-key creates both see nothing and both insert, each reporting `deduplicated: false`. Neither dedup index is unique and the create path takes no lock; in-process and SQLite are unaffected (`transactionConcurrency: "serialized"`). A unique index can't be the fix — `scope`/`windowMs`/`excludeChainIds` legitimately allow same-key coexistence. Preferred fix is a `dedup_lock` row-lock table acquired in its own statement (advisory locks blow the `max_locks_per_transaction` pool under batching, and a same-statement lock CTE is useless because the snapshot predates it). Only fixable at READ COMMITTED. Docs promise the guarantee unqualified and conformance has no concurrent case. See `design/concurrent-deduplication.md`.
- [TASK] Rework deduplication options — `key`/`scope` are the real surface; `excludeChainIds` and `windowMs` are workarounds that leak into every read surface and block the `listChains` dedup filter. `excludeChainIds` exists only because the complete callback runs _before_ `finishJob` writes the completion, so a self-scheduled recurrence still matches its own chain under `scope: "running"` — exposing post-completion, same-transaction scheduling (extend `execute` past `complete()`, or an after-completion callback) removes the need for it entirely while keeping the recurrence atomic. `windowMs` is throttling, not deduplication, and needs its own decision. Breaking (`major`). See `design/deduplication-options-rework.md`.
- [REF] minimize listing queries surface — make `typeName` a required partition key on `listChains`/`listJobs` (single, index-leading), one sort per status, drop uncoverable filters (`chainTypeName`, `chainId[]`/`jobId[]` on `listJobs`, completed-slice secondary predicates), add loose-scan `listJobTypeNames`/`listChainTypeNames` with open-work counts, and route cross-type work (cleanup) through per-type fan-out. See `design/minimize-listing-surface.md`.

Same verb, different subject/mechanism. Either rename one (e.g. the helper → `retryAfter`/`rescheduleSelf`) or at minimum document the distinction in the reference/guide docs

- [IDEA] Job variants — a tuple of variants under a single job type name, each declaring its own correlated `input` / `output` / `continueWith` / `blockers` / `entry`. The handler is one function whose `job` is a discriminated union over the variants, so narrowing `job.input` narrows `job.blockers`, the legal `continueWith` targets, and the expected output together. No `discriminator:` field, no tuple of handlers, no positional alignment — the runtime just delivers a job whose persisted shape matches exactly one variant and the user's `if`/`switch` narrows the rest. Lets a single workflow branch on runtime state without splitting into multiple job types.

# Triage

- [TASK] `wrapHandler` cannot observe attempt failures — the middleware chain wraps `runJobAttempt` (the executor), which catches handler/callback errors, reschedules, and returns normally, so a `catch` around `next()` never runs (only `finally` does). `wrapPrepare`/`wrapExecute`/`wrapComplete` do see errors, since they wrap the user callback directly — an undocumented asymmetry. Decide between documenting the current behavior, adding an `onAttemptError` hook, or moving the chain inward to wrap the handler. Any change that makes `catch` live is breaking (dead catch blocks become live, double-reporting against `jobAttemptFailed`). See `design/wrap-handler-error-visibility.md`.

# Short term

- [TASK] Attempt finalization rework — split the final phase from its outcome: `finalize` opens the transaction, `complete(output)` and `continueWith(...)` become sibling terminal actions inside it, each applying its transition (`finishJob`) inline rather than after the callback returns. Fixes three things at once: the outcome stops being inferred from the return value's shape (today's `TReturn extends output ? Completed : ContinuationJobs` degrades on `unknown`/`any`/overlapping outputs, cannot express void outputs, and silently tolerates `continueWith` + a returned output); code after the decision finally observes the completion write, which is the prerequisite for chain identity below (it unblocks removing `excludeChainIds`, without which the `running`-scope unique index cannot hold); and `complete` stops naming an outcome while acting as a phase. Net effect on the type surface is a deletion — `finalize` returns its callback's branded terminal verbatim, so no conditional type remains. Blast radius includes `wrapComplete` → `wrapFinalize` (the built-ins-win ctx guard grows a key), `completeChain`'s inner callback, every example and shared test suite. Open: `finalize` vs `settle`, observability buffer ordering, attempt-span boundaries around post-terminal work. Breaking (`major`). See `design/attempt-finalization-rework.md`.

Breaking (`major`); land before the major releases. See `design/chain-identity.md`.

- [IDEA] Job variants — a tuple of variants under a single job type name, each declaring its own correlated `input` / `output` / `continueWith` / `blockers` / `entry`. The handler is one function whose `job` is a discriminated union over the variants, so narrowing `job.input` narrows `job.blockers`, the legal `continueWith` targets, and the expected output together. No `discriminator:` field, no tuple of handlers, no positional alignment — the runtime just delivers a job whose persisted shape matches exactly one variant and the user's `if`/`switch` narrows the rest. Lets a single workflow branch on runtime state without splitting into multiple job types.

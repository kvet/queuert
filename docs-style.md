# Docs Style

## Overview

This document is the source of truth for writing and structuring the docs site in `docs/`, the way [Code Style](code-style.md) is for code. Read it before adding, moving or rewriting a page. The general rules in Code Style still apply to prose here: describe the current behavior only, use the domain vocabulary, and don't hard-wrap markdown.

## Site Layout

- The docs site is the private `docs/` workspace (SolidStart on Vite, static output). Run it with `pnpm docs:dev` and build it with `pnpm docs:build`; the build writes to `docs/.output/public`.
- Every page lives under `docs/src/content/docs/`, one file per URL slug (`guides/scheduling.mdx` → `/queuert/guides/scheduling/`, `index` files map to their directory).
- The Docs section (`getting-started/`, `guides/`, `integrations/`, `advanced/`) is hand-written markdown: `.md` for plain markdown, `.mdx` when the page uses components. These pages go through the MDX pipeline described below.
- The Examples (`examples/`), Compare (`comparison/`) and Benchmarks (`benchmarks/`) sections are `.tsx` pages. Each exports `export const meta = { title, description }` with string literals (plus `layout: "wide"` for a full-width page without the table of contents) and a default component whose body is ordinary JSX. Their data lives in `docs/src/data/`: `examples.ts`, `comparison.ts`, and `benchmarks.ts` (benchmark numbers and the shared test-setup rows).
- The home page is `docs/src/routes/index.tsx`. The changelog is generated at build time from the GitHub releases (`docs/plugins/changelog.ts`, prereleases skipped), and search is built from every page (`docs/plugins/search-index.ts`).
- The API reference under `/api/` is generated by TypeDoc from source TSDoc at build time (`docs/plugins/typedoc.ts`, one entry per package in `apiPackages` in `docs/src/docs/sections.ts`) into the git-ignored `docs/src/content/docs/api/`. Don't hand-write reference pages for symbols; fix the TSDoc instead (see Code Style, "Reference Documentation").
- Never put helper files under `docs/src/content/docs/`: every `.md`, `.mdx` and `.tsx` there is a page. Page-specific components go in `docs/src/components/`, data in `docs/src/data/`.
- Shared UI primitives (`Box`, `Row`, `Chip`, `StatusPill`, `StatusDot`, `Pips`, `IdChip`, …) come from the private `@queuert/ui` package (`packages-internal/ui`): `@queuert/ui/components`, `@queuert/ui/lib` (JSX-free helpers), `@queuert/ui/tokens.css` and `@queuert/ui/base.css`. Site styles live in `docs/src/styles/app.css` (Tailwind v4).

### Sidebar and Frontmatter

- Sidebar placement and order are set in `siteSections` in `docs/src/docs/sections.ts`. A page appears in the sidebar only once its slug is listed there.
- `docs/src/docs/sections.spec.ts` fails unless every page under `content/docs` (except `api/`) is listed in exactly one group and every listed slug has a file.
- Markdown pages start with YAML frontmatter: `title` (page title), `description` (subtitle and search summary) and `sidebar.order`. The spec also checks that the Guides, Integrations and Advanced groups in `sections.ts` follow `sidebar.order`, then title, so a new page gets both a frontmatter `sidebar.order` and its slug at the matching position in `sections.ts`.
- A leading `# Heading` in the markdown is dropped; the page title comes from frontmatter.

### The MDX Pipeline

`docs/plugins/mdx.ts` and `docs/plugins/content.ts` compile the markdown pages to Solid components. What a page can use:

- **Components** are imported from `@astrojs/starlight/components`, which resolves to the shim `docs/src/components/mdx/starlight.ts`. It exports `Aside`, `Badge`, `Card`, `CardGrid`, `LinkCard`, `FileTree`, `Steps`, `Tabs` and `TabItem`. Nothing else from Starlight exists.
- **Flow diagrams** are imported from `../../../components/diagram`, which resolves to the Solid port in `docs/src/components/diagrams/flow/Diagram.tsx`: `Diagram`, `Flow`, `Node`, `Arrow`, `Group`, `Loop` and `Rows`.
- **Asides**: `:::note`, `:::tip`, `:::caution` and `:::danger` blocks (with an optional `[Title]`, e.g. `:::tip[Heads up]`) become `Aside`.
- **Code blocks**: fenced blocks are highlighted with Shiki at build time and render as the site's `Code` component; `title="jobs.ts"` in the fence meta sets the box title.
- **Tables**: markdown tables are converted to row lists (`TableRows`), never rendered as `<table>`. The first column is the name, the last the description.
- **Images**: relative image paths (`../../../assets/…`) are bundled; put them in `docs/src/assets/`.
- **Links**: a relative link to a `.md`/`.mdx` file is rewritten to that page's URL. Absolute links include the `/queuert/` base.

`.mdx` files are excluded from oxfmt (`.oxfmtrc.json`), so keep their formatting tidy by hand.

## One Owner per Topic

Each topic is owned by exactly one page. Every other page that touches it says one sentence at most and links the owner inline, inside the sentence. Before writing a paragraph, check whether another page already owns it; if it does, link it instead. When you move a topic, move the content to its owner, delete it everywhere else, and rewrite the inbound links (there is no link checker, so `grep -rn "<old-slug>" docs/src` before you finish).

## Forbidden on Every Page

- `<table>` markup anywhere in the site code, API reference included. Structured data in `.tsx` pages and components is a data-driven list or card component authored as an array: `FieldList`, `KeyValueList`, `CardGrid`/`LinkCard`. Markdown tables in `.md`/`.mdx` pages are fine because the pipeline converts them.
- "Edit this page on GitHub" links and per-page actions (copy page as Markdown, open the page source).
- Interactive widgets that don't show the mechanism: a control that re-shows the same state, an editable playground with no point, decoration. A clear static figure beats a gimmick.

## Visual Language

- **Flat and dashboard-native**: one visual language across every figure, the same as the dashboard: `Box` with its title on the border, dashboard-style rows, `StatusPill`/`StatusDot`, blocker chips and pips, thin connectors. No isometric, 3D, offset shadows, gradients or grid backdrops. Reach for the dashboard's own representations before inventing a diagram shape.
- **Two system fonts, no web fonts**: the system sans stack for reading text (prose, navigation, descriptions, buttons) and the system monospace for structure and machine text (headings, uppercase labels, box titles, status pills, identifiers such as type names and IDs, JSON and code). Both come from `@queuert/ui/tokens.css` and are shared with the dashboard.
- **Status colors carry meaning only**: blocked violet, pending amber, running blue, completed grey.
- **Show state changes**, don't caption them: the figure moves a row from `pending` to `running` rather than saying so underneath.
- **Realistic names** in new figures and samples: provision-account, send-welcome-email, sync-to-crm, render-invoice-pdf, capture-payment, reserve-stock, ship-order, daily-digest. Never foo/bar.
- **Restraint**: at most one moving thing in view. Animations play once when scrolled into view, or are driven by the reader (step controls), then rest with a replay control; they never loop. The one exception is the landing hero chain, which loops slowly and pauses out of view. With reduced motion, figures show a static step.
- **Stable layout**: a figure never changes height while animating or switching tabs. Reserve the tallest state's space.
- **Readable sizes**: prose is 15px; text inside figures is at least 13px where it fits.
- **Every page works in light mode, dark mode and at 390px width** with no horizontal page overflow. Wide figures scroll inside their own box.

## Examples

- `docs/src/data/examples.ts` must list exactly the directories in `examples/` that have a `package.json`, and `docs/src/data/examples.spec.ts` checks it, along with each entry's services, key files, scripts and that it appears on its examples page (`docs/src/content/docs/examples/<page>.tsx`). Adding, renaming or removing an example updates `examples.ts` and its examples page in the same change.
- An example that demonstrates a guide links back to it through the `guide` field in `examples.ts`, and the guide links the example.
- Guide and example stay in sync per Code Style, "Guides and Examples Stay in Sync": every pattern the guide teaches runs in the example, and a change to one updates the other. Example naming and code conventions are in Code Style, "Examples".

## Accuracy

- Verify every claim against the source in `packages/*/src` (and `design/` where it exists) before writing it: option names, defaults, thrown error classes, status transitions, ordering. If the docs and the code disagree, the code wins; fix the docs, or report the bug.
- Code samples compile against the current API. Prefer copying the shape of the matching example over writing from memory.
- Use the domain vocabulary from Code Style: `head`/`tail`, `attempt`, `reschedule`, `continueWith`, and the four job statuses. No synonyms in prose or figure labels.
- Write the current behavior only, never "now" or "no longer".

## Verifying a Docs Change

- Run `pnpm docs:build` once: the dev server compiles only the pages you open, and the build compiles every page, including the generated API reference.
- Screenshot every page you changed in light, dark and at 390px (for example with Playwright against `pnpm docs:dev` at 1440×1000 and 390×844, reduced motion, full page), and look at the images. Check for console errors and horizontal overflow.
- For stepped or tabbed figures, click through every step and tab and confirm the figure's height stays fixed.
- From `docs/`, run `pnpm typecheck` and `pnpm test` (covers `sections.spec.ts`, `examples.spec.ts`, `benchmarks.spec.ts` and the plugin specs in `docs/plugins/`).
- Run `pnpm fmt` from the repo root, then re-check your diff: the oxlint autofix can add `async` or strip `await` on sync-or-async code.
- When the page cites an example you changed, run it (`pnpm --filter example-<name> start`).
- Dashboard screenshots embedded in the docs are regenerated per Code Style, "Dashboard Screenshots".

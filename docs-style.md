# Docs Style

## Overview

This document is the source of truth for writing and structuring the docs site in `docs/`, the way [Code Style](code-style.md) is for code. Read it before adding, moving or rewriting a page. The general rules in Code Style still apply to prose here: describe the current behavior only, use the domain vocabulary, and don't hard-wrap markdown.

## Site Layout

- The docs site is the private `docs/` workspace: Solid 2 in the start mode of `@solidjs/vite-plugin`, with file routes from `docs/src/routes` and a Nitro static prerender. Run it with `pnpm docs:dev` and build it with `pnpm docs:build`; the build writes to `docs/.output/public`. The build prerenders every page listed by `readPages()` plus the links it crawls, and fails on any page that errors.
- Links to site pages are plain `<a>` elements whose `href` goes through `siteHref` (`docs/src/docs/href.ts`), which adds the `/queuert` base: Solid Router treats an `href` starting with `/` as a full path and never adds the base itself. Markdown links, and literal `href="/queuert/…"` values in page data, already carry the base.
- Pages are server-rendered and then hydrated, so JSX is created only while a component renders: data holding JSX (notes, descriptions, labels) lives in a function the page calls once, never in a module-level value or in a prop expression read more than once. State restored from the browser is read through `createSyncedTabs()` (`docs/src/components/mdx/Tabs.tsx`, the synced tabs and the install picker) and `createPickedStack()` (`docs/src/stack.ts`, the stack filter), which read as unset until the calling component has hydrated, so the hydrating render matches the prerendered page; never read the stack or the synced-tab store directly in render. Check a change with `pnpm docs:dev`: the browser console reports any hydration mismatch.
- Every page lives under `docs/src/content/docs/`, one file per URL slug (`guides/scheduling.mdx` → `/queuert/guides/scheduling/`, `index` files map to their directory).
- The top bar lists Learn, Guides, Concepts, Integrations, API and Compare, with Blog beside the search box (no dropdown menus). Learn (`learn/`) is the landing page, What is Queuert, the six lesson steps and Use it in your app. The steps come in two groups (`learnGroups` in `docs/src/data/learn.ts`): Essentials, the four steps that teach Queuert's guarantees (first chain, transactional outbox, errors and retries, transactional completion) in about ten minutes, then Shaping chains (continuing a chain, job blockers). Keep the Essentials near ten minutes and all of Learn under half an hour; a topic that does not fit becomes a guide linked from Go further. Guides (`guides/`) opens with an overview page (`guides/index.tsx`, the top-bar target) listing its five goal groups, Shape workflows, Handle failure, Timing and load, Data and lifecycle, and Extend, with one line per guide. Concepts is `how-it-works/`, starting with the Glossary. Compare holds `comparison/` and, as its Benchmarks group, `benchmarks/`; its overview page (`comparison/index.tsx`) lists the Benchmarks and Alternatives groups the same way. Both overview pages render `<SectionIndex section>`, which lists a section's labelled sidebar groups in two columns at the normal article width, each page with its title and description. Each page appears in exactly one group. A section's overview page (Guides, Compare, Integrations, Blog) is an ungrouped first sidebar item: its group has an empty label, which the sidebar and the breadcrumb leave out. Titles, headings and sidebar labels use sentence case; identifiers stay as written, and every guide has one name in its title, the sidebar, the overview and links.
- The Learn, Guides and Concepts pages are hand-written markdown: `.md` for plain markdown, `.mdx` when the page uses components. These pages go through the MDX pipeline described below.
- The Integrations (`integrations/`), Compare (`comparison/`) and Benchmarks (`benchmarks/`) pages are `.tsx` pages. Each exports `export const meta = { title, description }` with string literals (plus `layout: "wide"` for a full-width page without the table of contents) and a default component whose body is ordinary JSX. Their data lives in `docs/src/data/`: `examples.ts` (the example rows of the integrations pages), `comparison.ts`, and `benchmarks.ts` (the benchmark charts' rows and the shared test-setup rows; it reads the numbers from each suite's `benchmarks/<suite>/results.md` and fails the build when one it shows is missing).
- Adapter pages (`integrations/state-adapters/<backend>` and, next, the notify adapters) share one template, in this order: `<AtAGlance>` (package, clients, isolation, pairs with), Quick start (driver tabs switching both the `index.ts` region and the copyable `provider.ts`, never folded), Run on your machine (`<RunOnYourMachine>`: the clone, install and start commands of the page's main example), Configure (the top three options shown, the rest and the options shared by every state adapter in a `<Details summary hint>`), Reference (one fold each for the schema, indexes, state provider, isolation levels, tuning, write fence and provider testing specifics; each fold's summary carries the old heading id so links to it keep working) and Examples (`<ExampleRows>`). What holds for every state adapter, such as the general write fence and provider testing rules, lives once on the State adapters overview, and a backend page keeps only its specifics and a link.
- The Blog (`blog/`) holds essays that teach a problem and the patterns that solve it, independent of Queuert's API: they use generic code and SQL rather than Queuert calls, so they don't go stale with the API, and they are not showcases, case studies or pitches. A post ends by linking the page that owns the Queuert side instead of restating it. Posts are markdown pages with a quoted `date: "YYYY-MM-DD"` beside `title` and `description` (no `sidebar.order`), shown under the title. `blog/index.tsx` lists the Posts group of `sections.ts`, which is ordered newest first; `sections.spec.ts` checks the dates and the order.
- The home page is `docs/src/routes/index.tsx`. Its hero embeds the runnable `examples/tutorial/src/hero.ts` with `<ExampleCode>` inside `<FirstChain>` (`docs/src/components/landing/FirstChain.tsx`), which replays the hand-written events of `docs/src/components/landing/firstChainEvents.ts` next to the code; `firstChainEvents.spec.ts` runs `hero.ts` through the tutorial's chain recorder and fails unless the events match, so a change to that chain changes both files. The changelog is generated at build time from the GitHub releases (`docs/plugins/changelog.ts`, prereleases skipped), and search is built from every page (`docs/plugins/search-index.ts`). After prerendering, `docs/plugins/site-files.ts` writes `sitemap.xml` (every page), `llms.txt` (every sidebar page and API package with its description) and `llms-full.txt` (the full text and code of every sidebar page, API reference excluded) from the built HTML, so a new page reaches them once it is in `sections.ts`. GitHub Pages serves the site under `/queuert/`, where crawlers never read a `robots.txt`, so the site has none.
- The API reference under `/api/` is generated by TypeDoc from source TSDoc at build time (`docs/plugins/typedoc.ts`, one entry per package in `apiPackages` in `docs/src/docs/sections.ts`) into the git-ignored `docs/src/content/docs/api/`. Don't hand-write reference pages for symbols; fix the TSDoc instead (see Code Style, "Reference Documentation").
- Pages embed real code from `examples/` with `<ExampleCode example="postgresql/state-pg" file="src/index.ts" region="adapter" />` (`docs/src/components/ExampleCode.tsx`), or library source (SQL, scripts) from `packages/` with `package="…"` in place of `example`. The tsx-pages plugin reads and highlights the file at build time for `.tsx` pages and the home page, and a remark step in `docs/plugins/mdx.ts` does the same for MDX pages, so the attributes are string literals and nothing is imported; `region` selects the lines between `// #region adapter` and `// #endregion` in that file, lines between `// #hide` and `// #endhide` are elided (code the file needs to run but the docs leave out), and marker lines never appear in the output. Prefer embedding an example over a hand-written snippet whenever an example covers the code, so the docs compile with the examples.
- Learn lessons (`learn/`) are MDX pages: a few paragraphs teaching one idea, then a `<TryIt lesson="first-chain">` line stating the exercise. The lesson steps set `layout: step`: no left sidebar, a `Stepper` (`docs/src/components/tutorial/Stepper.tsx`) across the top of the page (a "Learn" link back to the landing page, then the steps numbered 1–6 as links with the open one highlighted and the passed or marked-read ones ticked; below `xl` only the numbers and a "Step N of 6" line with the open title show) and the prev/next pager at the bottom. The Learn landing, What is Queuert and Use it in your app keep the normal docs layout. Exercises live only on the lesson steps; guides show their example code and carry no exercise. The task is always open: `<TryIt>` renders a "Your task: …" callout pointing at the panel, worded imperatively with a lowercase start and code spans. The build exports the lesson's files from the page module (`exercise`, written by the remark step in `docs/plugins/mdx.ts`, one `<TryIt>` per page), and the step page renders `<Exercise>` (`docs/src/components/tutorial/Exercise.tsx`) in its panel, sticky beside the prose from 1024px and stacked below it under 1024px. The lesson steps tick on the Learn landing page (`StepProgress`) and in the stepper once the lesson passes or the reader marks the step read, kept in `localStorage` and read after hydration. The remark step fills the exercise from `examples/tutorial/src/<lesson>/` (`docs/plugins/exercise.ts`): `start/` (what the reader edits, `index.ts` the entry), `solution/` (the same file names, loaded by **Solve**) and `check.ts` (throws a hint unless the run's logs show the lesson solved). Every lesson runs on a real database in the browser, PostgreSQL through PGlite or SQLite through sql.js: it imports `openDatabase` from `./db.ts`, which opens the database, applies Queuert's migration and returns the `stateAdapter` and a `sql` tagged template for the lesson's own tables, so a lesson's `index.ts` is the same on both. `start/` and `solution/` each keep a one-line `db.ts` that re-exports `src/db/postgres.ts`, so the lessons also run under Node; the exercise swaps it for `src/db/<database>.ts` of the reader's pick, shown read-only beside the reader's files. The **Database** chips follow the install picker's `state` key: SQLite when it is SQLite, PostgreSQL otherwise. In the browser a long-lived compiler worker type-checks the reader's files against TypeScript's `esnext` and `webworker` libs and the declarations of `queuert`, `@queuert/postgres`, `@queuert/sqlite`, PGlite, sql.js and the state providers of the `postgresql/state-pglite` and `sqlite/state-sql-js` examples (`docs/plugins/tutorial-types.ts`, so the three Queuert packages are built before the docs), feeds the editor's diagnostics, hover and completions, and refuses to run code with type errors; each run then gets a fresh runner worker with `queuert` bundled and the picked database's driver and adapter loaded, terminated once `index.ts` and the check finish or after 15 seconds. The reader's draft is kept per lesson in `localStorage`. `docs/src/components/tutorial/exercises.spec.ts` fails unless every lesson type-checks cleanly on both databases, and on both its solution passes its check and its start does not.
- Per-driver code goes in `<Tabs syncKey="…">`. Panels take their own height; never reserve the tallest panel's height. The same `syncKey` and labels keep every page on the reader's driver (`postgres-driver`, `sqlite-driver`, `mysql-driver`, `redis-driver`, `validation-library`, `logger`, `test-runner`), and the pick is saved in the browser, so it survives navigation and later visits. The Use it in your app page's picker (`docs/src/components/InstallPicker.tsx`, options in `docs/src/data/installation.tsx`) stores its state adapter, notify adapter and package manager under the `state`, `notify` and `pkg` keys. `PickedTabs pick="state"` or `pick="notify"` (same file) shows the `TabItem` whose label is the picked option, with the picker's own fallback when a stored notify pick does not fit the state adapter, so its tab labels equal the option labels in `installation.tsx`.
- Benchmark rows and series that measure one backend carry `backend` (`docs/src/stack.ts` lists the ids). `StackFilter` on a benchmark page lets the reader pick the backends they use; the pick is saved in the browser and shared by every benchmark page, an inline head script puts it on `<html data-stack>` before the first paint, and CSS hides the other backends' rows, so filtering never flashes. Untagged rows (packages that are not adapters) always show; picking nothing shows every backend. A `BenchChart` is one scenario with the adapters (or packages) as its rows, one bar each: data measured over several scenarios keeps them as series and each page charts one with `seriesOf`. Rows measured under different conditions (state adapters versus notify adapters, or each query on Query performance) go in separate labelled groups with `scalePerGroup`.
- Never put helper files under `docs/src/content/docs/`: every `.md`, `.mdx` and `.tsx` there is a page. Page-specific components go in `docs/src/components/`, data in `docs/src/data/`.
- Shared UI primitives (`Box`, `Row`, `Chip`, `StatusPill`, `StatusDot`, `Pips`, `IdChip`, `ChoiceChips`, `ToggleChips`, …) come from the private `@queuert/ui` package (`packages-internal/ui`), shared with the dashboard: `@queuert/ui/components`, `@queuert/ui/lib` (JSX-free helpers), `@queuert/ui/tokens.css` and `@queuert/ui/base.css`. Site styles live in `docs/src/styles/app.css` (Tailwind v4).
- Widgets with keyboard behavior are built on Kobalte (`@kobalte/core`), never hand-rolled: tab sets (`Tabs`, the mobile drawer's sections) on its `Tabs`, a row of option buttons on `ChoiceChips` (pick one) or `ToggleChips` (pick any), both on its `ToggleGroup`. Style its parts through the `data-selected` and `data-pressed` attributes it sets. Its overlays (`Dialog`, `Popover`, `Tooltip`, `DropdownMenu`) are not used yet: on the current alpha the dialog ignores Escape and the popover never renders its content.

### Sidebar and Frontmatter

- Sidebar placement and order are set in `siteSections` in `docs/src/docs/sections.ts`. A page appears in the sidebar only once its slug is listed there.
- `docs/src/docs/sections.spec.ts` fails unless every page under `content/docs` (except `api/`) is listed in exactly one group and every listed slug has a file.
- Markdown pages start with YAML frontmatter: `title` (page title), `description` (subtitle and search summary) and `sidebar.order`. The spec also checks that the Guides and Concepts sections in `sections.ts` follow `sidebar.order`, then title across their groups, so a new page gets both a frontmatter `sidebar.order` and its slug at the matching position in `sections.ts`.
- A leading `# Heading` in the markdown is dropped; the page title comes from frontmatter.
- Every route sets its head tags through `PageMeta` (`docs/src/components/PageMeta.tsx`): the title, the description, the canonical URL and the Open Graph and Twitter card tags. The canonical and link-preview URLs are built from `siteUrl` in `docs/src/docs/site.ts`, which also sets the Vite `base`. The description is what search results, link previews and `llms.txt` show, so it says what the page covers in one sentence.

### The MDX Pipeline

`docs/plugins/mdx.ts` and `docs/plugins/content.ts` compile the markdown pages to Solid components. What a page can use:

- **Components** are imported from `@astrojs/starlight/components`, which resolves to the shim `docs/src/components/mdx/starlight.ts`. It exports `Aside`, `Badge`, `Card`, `CardGrid`, `LinkCard`, `FileTree`, `Steps`, `Tabs` and `TabItem`. Nothing else from Starlight exists.
- **Flow diagrams** are imported from `../../../components/diagram`, which resolves to the Solid port in `docs/src/components/diagrams/flow/Diagram.tsx`: `Diagram`, `Flow`, `Node`, `Arrow`, `Group`, `Loop`, `Rows`, `Transition`, and for events in time order `Timeline` (one lane per actor), `Step` (an event on a lane) and `Mark` (a moment across all lanes, such as a lease running out). Figures have no colour of their own: a job in a status gets `status` on its `Node` (a `StatusPill`), a status change goes in a `sub` as `<Transition from="pending" to="running" />` (`via` adds a middle status), and an `Arrow`, `Step` or `Mark` on a failure path takes `failure`. Everything else stays neutral.
- **Asides**: `:::note`, `:::tip`, `:::caution` and `:::danger` blocks (with an optional `[Title]`, e.g. `:::tip[Heads up]`) become `Aside`.
- **Folds**: `<Details summary="…" hint="…">` (`docs/src/components/mdx/Details.tsx`, registered with the MDX components, no import) is a native `<details>` that folds a long reference block so the page stays short. Fold schemas, indexes, provider members, catalogues and tuning tables; never fold the first diagram, the main example or a Quick start. The `summary` line says what is inside and the `hint` says how much (`12 columns`, `8 indexes`). The folded content is rendered into the prerendered HTML, so search and `llms-full.txt` still contain it, and a URL `#anchor` that targets an element inside a fold opens it after hydration.
- **Example code**: `<ExampleCode>` needs no import; the build fills it in as described under Structure.
- **Code blocks**: fenced blocks are highlighted with Shiki at build time and render as the site's `Code` component; `title="jobs.ts"` in the fence meta sets the box title.
- **Tables**: markdown tables are converted to row lists (`TableRows`), never rendered as `<table>`. The first column is the name, the last the description.
- **Images**: relative image paths (`../../../assets/…`) are bundled; put them in `docs/src/assets/`.
- **Links**: a relative link to a `.md`/`.mdx` file is rewritten to that page's URL. Absolute links include the `/queuert/` base.

`.mdx` files are excluded from oxfmt (`.oxfmtrc.json`), so keep their formatting tidy by hand.

## One Owner per Topic

Each topic is owned by exactly one page. Every other page that touches it says one sentence at most and links the owner inline, inside the sentence. Before writing a paragraph, check whether another page already owns it; if it does, link it instead. When you move a topic, move the content to its owner, delete it everywhere else, and rewrite the inbound links (there is no link checker, so `grep -rn "<old-slug>" docs/src` before you finish).

## Forbidden on Every Page

- `<table>` markup anywhere in the site code, API reference included. Structured data in `.tsx` pages and components is a data-driven list or card component authored as an array: `FieldList`, `KeyValueList`, `CardGrid`/`LinkCard`. Markdown tables in `.md`/`.mdx` pages are fine because the pipeline converts them.
- "Edit this page on GitHub" links and per-page actions (copy page as Markdown, open the page source).
- Interactive widgets that don't show the mechanism: a control that re-shows the same state, an editable playground with no point, decoration. A clear static figure beats a gimmick.

## Visual Language

- **Flat and dashboard-native**: one visual language across every figure, the same as the dashboard: `Box` with its title on the border, dashboard-style rows, `StatusPill`/`StatusDot`, blocker chips and pips, thin connectors. No isometric, 3D, offset shadows or gradients, and no grid backdrops behind figures (the square grid behind the home hero and the site footer is the one allowed exception). Reach for the dashboard's own representations before inventing a diagram shape.
- **Two system fonts, no web fonts**: the system sans stack for reading text (prose, navigation, descriptions, buttons) and the system monospace for structure and machine text (headings, uppercase labels, box titles, status pills, identifiers such as type names and IDs, JSON and code). Both come from `@queuert/ui/tokens.css`, the same tokens the dashboard uses.
- **Status colors carry meaning only**: blocked violet, pending amber, running blue, completed grey.
- **Show state changes**, don't caption them: the figure moves a row from `pending` to `running` rather than saying so underneath.
- **Realistic names** in new figures and samples: provision-account, send-welcome-email, sync-to-crm, render-invoice-pdf, capture-payment, reserve-stock, ship-order, daily-digest. Never foo/bar.
- **Restraint**: at most one moving thing in view. Animations play once when scrolled into view, or are driven by the reader (step controls), then rest with a replay control; they never loop. With reduced motion, figures show a static step.
- **Stable layout**: a figure never changes height while animating or switching its own steps or tabs. Reserve the tallest state's space. Code `<Tabs>` are not figures: each panel takes its own height.
- **Readable sizes**: prose is 15px; text inside figures is at least 13px where it fits.
- **Every page works in light mode, dark mode and at 390px width** with no horizontal page overflow. Wide figures scroll inside their own box.

## Examples

- `docs/src/data/examples.ts` lists the stack and integration examples that an integrations page shows in its `<ExampleRows>`, named by their path under `examples/` (`postgresql/state-pg`). `docs/src/data/examples.spec.ts` checks each entry's services, key files, scripts and package name, and that it appears on an integrations page. Adding, renaming or removing such an example updates `examples.ts` and the integrations page in the same change.
- An entry's `guide` field links the integrations page that owns it. Guides embed their code from `examples/guides/` with `<ExampleCode example="guides">` and are not listed in `examples.ts`.
- Guide and example stay in sync per Code Style, "Guides and Examples Stay in Sync": every pattern the guide teaches runs in the example, and a change to one updates the other. Example naming and code conventions are in Code Style, "Examples".

## Accuracy

- Verify every claim against the source in `packages/*/src` (and `design/` where it exists) before writing it: option names, defaults, thrown error classes, status transitions, ordering. If the docs and the code disagree, the code wins; fix the docs, or report the bug.
- Code samples compile against the current API. Prefer copying the shape of the matching example over writing from memory.
- Use the domain vocabulary from Code Style: `head`/`tail`, `attempt`, `reschedule`, `continueWith`, and the four job statuses. No synonyms in prose or figure labels.
- Write the current behavior only, never "now" or "no longer".

## Verifying a Docs Change

- Run `pnpm docs:build` once: the dev server compiles only the pages you open, and the build compiles every page, including the generated API reference.
- Screenshot every page you changed in light, dark and at 390px (for example with Playwright against `pnpm docs:dev` at 1440×1000 and 390×844, reduced motion, full page), and look at the images. Check for console errors and horizontal overflow.
- For stepped or tabbed figures, click through every step and tab and confirm the figure's height stays fixed.
- From `docs/`, run `pnpm typecheck` and `pnpm test` (covers `sections.spec.ts`, `examples.spec.ts` and the plugin specs in `docs/plugins/`).
- Run `pnpm fmt` from the repo root, then re-check your diff: the oxlint autofix can add `async` or strip `await` on sync-or-async code.
- When the page cites an example you changed, run it (`pnpm --filter example-<name> start`).
- The dashboard page embeds the live dashboard; its demo data follows Code Style, "Dashboard Demo".

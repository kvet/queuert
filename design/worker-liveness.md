# Worker liveness

Move attempt ownership from the job row to the worker. Workers register themselves in the database, hold a single lease that a process-level heartbeat renews, and a job's `attemptBy` is a reference to a live worker row instead of a self-contained per-job deadline.

## Problem

Today liveness is tracked per job. Every running job carries `attempt_until`, every in-flight attempt runs its own heartbeat (`extendJobAttempt` on a timer inside `runJobProcess`), and the worker loop reclaims one expired job per iteration (`reclaimExpiredJobAttempt`).

That has a handful of costs:

- **Write amplification.** A worker with concurrency `N` issues `N` heartbeat transactions per interval, each one an `UPDATE` on a hot job row (plus an index write on `job_running_idx`). The information carried by all of them is identical: "this process is alive".
- **Per-job timeout tuning.** `attemptConfig.timeoutMs` is really "how long may this process be unreachable before we give the job to someone else", but it is configured per processor, so the same process-level fact is expressed once per job type, and a long-running job type has to widen the window for everything it touches.
- **Self-reclaim races.** Because a worker can reclaim its own jobs, `reclaimExpiredJobAttempt` needs `ignoredJobIds` to exclude the jobs the caller is currently running — a workaround for a question ("is the owner alive?") the job row cannot answer.
- **No worker inventory.** Nothing in the database knows which workers exist. `attemptBy` is an opaque `name-uuid` string; there is no way to list workers, show them in the dashboard, or tell "crashed" from "never existed".
- **Type-scoped reclamation.** Reclaim only covers job types the reclaiming worker is registered for. A dead worker's jobs of a type nobody else processes stay `running` forever.

## Solution

One row per live worker process, one lease per worker, one heartbeat per process.

- A `worker` table holds `id`, `name`, `registered_at`, `registered_until`.
- `job.attempt_by` holds a worker `id`; `job.attempt_until` is dropped.
- A running job is "live" exactly when its worker's lease is live. Reclamation becomes a worker-level operation: expire the worker, return its jobs to `pending` as a failed attempt, delete the worker row.

Everything else about job processing — `refetchJobLocked`, `JobTakenByAnotherWorkerError`, `listenJobAttemptLost`, backoff — is unchanged.

### Schema

Part of `001_initial_schema` in both adapters — pre-1.0, no incremental migration. Existing databases go through the same `legacy-upgrade` import path, which simply stops carrying `attempt_until` over.

```sql
CREATE TABLE IF NOT EXISTS {{schema}}.{{table_prefix}}worker (
  registered_at     timestamptz NOT NULL DEFAULT now(),
  registered_until  timestamptz NOT NULL,
  id                uuid PRIMARY KEY,
  name              text
);

CREATE INDEX IF NOT EXISTS {{table_prefix}}worker_expired_idx
ON {{schema}}.{{table_prefix}}worker (registered_until);
```

**Naming.** The lifecycle methods below are `startWorker` / `stopWorker`, which sits slightly off `registered_at` / `registered_until`. Two options: keep the columns as specified and treat "the worker row" as the noun (what this doc does), or rename them to `started_at` / `lease_until`, which matches the method names and makes `extendWorkerLease` name the column it moves. Worth deciding before the schema ships — persisted names are the expensive kind.

The worker id is always a UUID generated by the worker itself, independent of the configurable `{{id_type}}` used for jobs — worker ids are never user-supplied, so there is nothing to make pluggable. `name` is the optional human label previously baked into `attemptBy`; it now lives in its own column instead of being string-concatenated into the id.

Job table changes:

- Drop `attempt_until`.
- `job_running_idx` becomes `(type_name, attempt_at) WHERE status = 'running'` — the reclaim scan no longer touches the job table by deadline, but the dashboard still orders running jobs.
- `attempt_by` keeps its `text` type and gains no foreign key (consistent with `job_blocker`, which also references jobs without one). Referential integrity is maintained by the lease gate below, not by the engine.

No index on `attempt_by`: reclaim of a single worker's jobs is a `WHERE attempt_by = $1 AND status = 'running'` scan, which for realistic worker counts is served by `job_running_idx` plus a filter. If it shows up in benchmarks, a partial `(attempt_by) WHERE status = 'running'` index is the follow-up.

### State adapter surface

Removed: `extendJobAttempt`, `reclaimExpiredJobAttempt`.

Added:

```ts
export type StateWorker = {
  id: string;
  name: string | null;
  registeredAt: Date;
  registeredUntil: Date;
};
```

```ts
/** Starts a worker, taking a lease that expires `leaseMs` from now. A duplicate id throws. */
startWorker: (
  params: {
    workerId: string;
    name?: string | null;
    leaseMs: number;
  } & WriteTxContextParam<TTxContext>,
) => Promise<StateWorker>;

/**
 * Extends a worker's lease. Returns `undefined` when the worker row is gone or already
 * expired — an expired lease is forfeit and cannot be renewed, because a reclaimer may
 * already be handing its jobs to someone else.
 */
extendWorkerLease: (
  params: {
    workerId: string;
    leaseMs: number;
  } & WriteTxContextParam<TTxContext>,
) => Promise<StateWorker | undefined>;

/**
 * Stops a worker, releasing any attempt it still holds, exactly as expiry would.
 * Returns `undefined` when no worker row matches the id.
 */
stopWorker: (
  params: {
    workerId: string;
  } & WriteTxContextParam<TTxContext>,
) => Promise<{ worker: StateWorker; jobs: StateJob[] } | undefined>;

/** Gets a worker by id, `undefined` when it is gone. */
getWorker: (params: { workerId: string } & ReadTxContextParam<TTxContext>) =>
  Promise<StateWorker | undefined>;

/**
 * Deletes up to `limit` expired workers and returns each one's running jobs to `pending`,
 * recorded as a failed attempt. Returns each deleted worker with the jobs it was holding,
 * oldest lease first.
 */
reclaimExpiredWorkers: (
  params: {
    limit: number;
  } & WriteTxContextParam<TTxContext>,
) => Promise<{ worker: StateWorker; jobs: StateJob[] }[]>;

/** Lists workers, ordered by `registeredAt`. */
listWorkers: (
  params: {
    orderDirection: OrderDirection;
    page: PageParams;
  } & ReadTxContextParam<TTxContext>,
) => Promise<Page<StateWorker>>;
```

`stopWorker` and `reclaimExpiredWorkers` share one primitive so a graceful stop and a crash leave the database in the same shape; the only difference is which rows are selected, and both return the jobs they released. `stopWorker` normally finds nothing to release (the worker drains first), but it must still release rather than delete-and-orphan: a `running` job whose `attempt_by` names a nonexistent worker would never be reclaimed by anything.

Released jobs are written as a failed attempt, not a silent requeue, which is a behavior change from today's reclaim:

- `status = 'pending'`, `attempt_at = NULL`, `attempt_by = NULL`
- `last_attempt_at = now()`, `last_attempt_error = 'Worker stopped unexpectedly'` (serialized through the same shape `rescheduleJobs` uses for `error`)
- `scheduled_at = now()` — no backoff. The job never got to run; the failure is the worker's, not the job's. `attempt` was already incremented by `startJobAttempt`, so a crash-looping worker still exhausts nothing but attempt count, which is the honest record.

`reclaimExpiredWorkers` is **not** type-scoped. A worker's jobs are released whether or not the reclaimer processes those types — that is the fix for jobs stranded on a type no live worker handles. The caller therefore has to notify per distinct `typeName` of the returned jobs rather than for its own type list.

`limit` bounds a single transaction. The per-worker job count is bounded by that worker's concurrency, so `limit: 1` (the worker loop's value) updates at most `concurrency` rows.

### Claiming under a lease

`startJobAttempt` gains a lease gate in the same statement:

```sql
worker_lease AS (
  SELECT id FROM {{schema}}.{{table_prefix}}worker
  WHERE id = $2 AND registered_until > now()
  FOR SHARE
)
```

and the `UPDATE` is additionally gated on `EXISTS (SELECT 1 FROM worker_lease)`.

The `FOR SHARE` is load-bearing, not decoration. Without it, this interleaving orphans a job:

1. Reclaimer selects expired worker `W`, updates `W`'s running jobs, deletes `W`.
2. Concurrently, `W` claims job `J` — its `EXISTS` check ran against a snapshot where `W` was still present.
3. `W`'s claim commits after the reclaimer's job `UPDATE` ran. `J` is `running`, owned by a worker row that no longer exists.

With `FOR SHARE` on the claim side and `FOR UPDATE SKIP LOCKED` on the reclaim side, the reclaimer's worker-row lock waits for the in-flight claim to commit; its subsequent job `UPDATE` (a new statement, new snapshot under READ COMMITTED) then sees `J` and releases it. SQLite serializes writers, and the in-process adapter runs under its async RW lock, so both get this for free — the lock is a PostgreSQL concern that the conformance suite pins for everyone.

A claim that returns `undefined` stays ambiguous ("nothing to do" vs. "lease gone"); the lease heartbeat, not the claim, is what detects loss. Worst case a worker spins through idle iterations until the next heartbeat.

## Worker lifecycle

`createInProcessWorker` replaces per-processor `attemptConfig` with a worker-level lease:

```ts
createInProcessWorker({
  client,
  workerName,
  concurrency,
  lease: { durationMs: 60_000, heartbeatMs: 20_000 },
  // attemptConfig / defaults.attemptConfig removed
});
```

Defaults: `durationMs: 60_000`, `heartbeatMs: 20_000` — three renewal opportunities per lease, so a single slow or failed renewal does not cost the lease. `workerName` keeps its `/^[A-Za-z0-9._-]+$/` validation and now lands in `worker.name`; the worker id is a bare `randomUUID()`.

### States

```
         startWorker                              stopWorker
  start ─────────────▶ running ── stop() ─▶ draining ──────────▶ stopped
                          │  ▲                  │
              lease lost  │  │ startWorker      │ lease lost
                          ▼  │ (new id, backoff)▼
                       draining (forfeit) ──────┘
```

**start()**

1. `startWorker({ workerId, name, leaseMs })` in its own transaction, then emit `workerStarted`. A failure here fails `start()` — the process has nothing to recover into yet.
2. Start the lease manager.
3. Run the main loop.

**Lease manager.** Every `heartbeatMs`, `extendWorkerLease` in its own transaction.

- Renewed → emit `workerLeaseExtended`, continue.
- `undefined` → the lease is lost; enter recovery.
- Throws (database unreachable) → retry on the loop's backoff. If `registeredUntil` passes while retrying, stop retrying and enter recovery: the lease is expired regardless of whether we can see the database, and treating an unreachable database as "still ours" is exactly how two workers end up running the same job.

**Main loop.** Unchanged except for step 2:

1. Fill: `startJobAttempt` until empty or no idle slots.
2. Reclaim: `reclaimExpiredWorkers({ limit: 1 })` when idle slots remain. For each swept worker, emit `workerReclaimed`, then `jobAttemptReclaimed` per returned job, then `provideWakeHint(typeName, count)` + `notifyJobScheduled(typeName)` per distinct type and `notifyJobAttemptLost(jobId)` per job.
3. Wait, repeat.

`ignoredJobIds` is gone. A worker may reclaim itself: if its own lease has expired then it is, by definition, dead, and the honest response is to release the jobs and discover the loss on the next heartbeat.

**stop()**

1. Emit `workerStopping` and abort the stop signal — in-flight attempts see `"worker_stopping"`.
2. Stop filling; drain the executor.
3. Stop the lease manager.
4. `stopWorker`, releasing anything still held (normally nothing), then emit `workerStopped`.

The lease manager keeps renewing throughout the drain, so a long graceful shutdown does not lose jobs mid-flight.

**Recovery.** On lease loss:

1. Abort in-flight attempts with the new hard reason `"worker_lease_lost"`, stop filling slots, and drain. Those attempts will mostly fail on their next `refetchJobLocked` with `JobTakenByAnotherWorkerError` (already swallowed by `handleJobHandlerError`) — the abort makes it prompt and explicit rather than a surprise at complete time.
2. Emit `workerLeaseLost`, then `workerStopping`; stop the lease manager. When the drain finishes, emit `workerStopped` — there is no `stopWorker` call to make, because the row is the reclaimer's to delete.
3. On `recoveryBackoffConfig`, `startWorker` with a **freshly generated** UUID. The old id belongs to a row that a reclaimer owns; reusing it risks colliding with a row that has not been swept yet.
4. On success, emit `workerStarted` for the new id and resume the main loop.

The worker never exits on lease loss — a lease is lost to a GC pause or a database blip far more often than to an actually dead process, and a process that kills itself over a 60-second stall is worse than one that starts a new worker.

### Trade-off: hung jobs

Per-job deadlines gave a crude hard timeout: a job that hung past `timeoutMs` was released even if the process was healthy. A process-level lease deliberately gives that up — a live process holds its jobs indefinitely. This is the correct semantics (the job _is_ being worked on, and reclaiming it would duplicate work), but it does mean a deadlocked handler parks a slot until the process is restarted. Real hard timeouts need handler-side cancellation or worker threads, which is already tracked separately in `TODO.md`.

## Observability

The worker row and the worker process have the same lifetime, so they share one pair of events rather than getting two. `workerStarted` is emitted after `startWorker` commits, `workerStopped` after `stopWorker` commits — no separate `workerRegistered` / `workerDeregistered`.

Removed: `jobAttemptExtended`, `jobAttemptExpired`.

Changed:

- `workerStarted({ workerId, workerName, jobTypeNames, registeredUntil })` — gains `workerName` and `registeredUntil`.
- `workerStopping({ workerId, workerName })` / `workerStopped({ workerId, workerName })` / `workerError({ workerId, workerName }, error)` — gain `workerName`, since the label is no longer recoverable from the id string.

Added:

- `workerLeaseExtended({ workerId, workerName, registeredUntil })`
- `workerLeaseLost({ workerId, workerName })`
- `workerReclaimed({ workerId, workerName, reclaimedWorkerId, reclaimedWorkerName, jobCount })` — this worker swept a dead one.

Recovery emits no event of its own. A lease loss reads as `workerLeaseLost` → `workerStopping` → `workerStopped` → (backoff) → `workerStarted` with a new `workerId`, which is the same shape as a crash-and-restart and needs no extra vocabulary to interpret. Every `workerStarted` is therefore matched by exactly one `workerStopped`, and every worker-scoped event carries the id of the worker row that was live when it was emitted.

### `jobAttemptReclaimed`

Yes — `reclaimExpiredWorkers` returns the released jobs as full `StateJob` rows, so the reclaiming worker can emit `jobAttemptReclaimed(stateJob, { workerId, reclaimedFromWorkerId })` per job, exactly as it does today for the single job that `reclaimExpiredJobAttempt` returns. The rows are needed regardless of observability: the caller has to read each job's `typeName` to wake the right listeners and each `id` to fire `notifyJobAttemptLost`. The volume is bounded by the dead worker's concurrency times `limit`.

`workerReclaimed` earns its place next to it because it is the only signal when an **idle** worker dies — no jobs held, no `jobAttemptReclaimed`, and without it a crashed idle process leaves no trace anywhere. It also gives the per-job events their parent: `jobCount` says how many `jobAttemptReclaimed` events belong to that sweep.

## API and surface changes

Breaking, all bundled into one changeset:

- `Job.attemptUntil` removed from the public job shape.
- `listJobs` / `client.listJobs` lose `orderBy: "attemptUntil"` for `status: "running"`; `attemptAt` and `createdAt` remain. The dashboard's running-jobs view switches to `attemptAt`.
- `createProcessors({ attemptConfig })` and `createInProcessWorker({ defaults: { attemptConfig } })` removed, replaced by `createInProcessWorker({ lease })`. `AttemptConfig` and `createAttemptHeartbeat` are deleted.
- `StateAdapter` loses `extendJobAttempt` / `reclaimExpiredJobAttempt` and gains `startWorker`, `stopWorker`, `getWorker`, `extendWorkerLease`, `reclaimExpiredWorkers`, `listWorkers` — a breaking change for any custom adapter.
- New `JobAbortReason` member `"worker_lease_lost"` (hard/error-level, so it also lands in the `HardJobAbortReason` split tracked in `TODO.md`).

## Prototype scope

In:

- Core: `StateAdapter` surface, in-process adapter, worker lifecycle (start / lease manager / recovery / stop), observability events, error and abort plumbing.
- PostgreSQL and SQLite adapters: schema, the six methods, the `startJobAttempt` lease gate, legacy-upgrade and fast-seed fixups.
- Conformance: delete `extend-job-attempt.ts` and `reclaim-expired-job-attempt.ts`; add `worker-lifecycle.ts` (start / get / extend / list / stop, including the "expired lease cannot renew" case and "stop releases a still-held job") and `reclaim-expired-workers.ts` (releases across types, marks the failed attempt, deletes the worker row, returns the released jobs, respects `limit`, and the claim-vs-reclaim race).
- Suites: `attempt-reclaimer.test-suite.ts` becomes `worker-liveness.test-suite.ts` — a killed worker's jobs get picked up by another, a long job survives its lease window while the heartbeat runs, recovery starts a new worker and resumes, stop removes the worker row.
- Docs: `advanced/in-process-worker.md` (lifecycle, reclamation), `advanced/adapters.md` (txCtx method lists), `advanced/postgres-internals.md` / `sqlite-internals.md` (schema), `advanced/logging.md` (events). Changeset covering core + postgres + sqlite + dashboard.

Out:

- Dashboard workers view. `listWorkers` exists for it, but the UI is a separate task.
- OTEL semantic-convention naming for the new worker events — they get adapter methods, not a metrics redesign.
- Any per-job hard timeout.
- An `attempt_by` index; revisit after benchmarks.

## Open questions

1. **`limit` for `reclaimExpiredWorkers` in the main loop.** `1` keeps iterations short and matches today's one-job-per-iteration behavior. If a deployment restarts fifty workers at once, sweeping is slow (one per loop iteration per live worker). A small constant like `4` is probably better; leaving it at `1` for the prototype and measuring.
2. **Stale-worker cap.** Nothing bounds the `worker` table if reclamation never runs (e.g. every worker is down). Expired rows are only swept by live workers. That is self-correcting — the table only grows while nothing is processing — but the built-in cleanup design may want to sweep long-expired worker rows too.
3. **Should `getWorker` be on the public client?** The dashboard needs `listWorkers` through some route; whether individual worker lookup is worth a client method can wait for the dashboard task.

Most background work follows a write: a user signs up, then gets a welcome email. When the job and the user are two separate writes, a failure between them leaves one without the other. The transactional outbox removes the gap by saving the job in the same transaction as the data.

With a separate queue, the two writes can drift apart in either order. Queue the email first and a failed save sends it to a user who does not exist; save first and a crash before the queue call leaves a user who never hears from you. [The dual-write problem](../../blog/dual-write-problem/) walks through each case. The outbox pattern writes the message into a table of the same database instead, inside the transaction that saves the data, and a relay delivers it after the commit. With Queuert the jobs table is the outbox and the worker is the relay, so there is no separate queue to keep in sync.

Passing the same `txCtx` to your own SQL and to `client.createChain` puts both writes in one transaction: the job commits with the user and rolls back with it. A worker only ever sees committed jobs.

Below, `signUp` creates the chain in one transaction and saves the user in a second. The second sign-up reuses ada's email, so its `INSERT` fails on the `UNIQUE` constraint, but its chain has already committed and the worker emails a user who was never saved.

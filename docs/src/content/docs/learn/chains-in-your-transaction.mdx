A chain you create next to your own write commits or rolls back with it: the job exists if the write is saved, and never exists if it is not.

<Diagram label="A transaction holds the application write and createChain; commit leaves a pending job for the worker, rollback leaves nothing">
  <Flow>
    <Group title="transaction" dashed>
      <Flow>
        <Node sub="your own write">save user</Node>
        <Arrow />
        <Node sub="same txCtx">client.createChain(…)</Node>
      </Flow>
    </Group>
    <Rows spine columns="minmax(6rem, auto) auto">
      <Flow>
        <Arrow label="COMMIT" />
        <Node status="pending">send-welcome-email</Node>
      </Flow>
      <Flow>
        <Arrow label="ROLLBACK" failure />
        <Node variant="ghost" sub="no chain, no user">nothing</Node>
      </Flow>
    </Rows>
  </Flow>
</Diagram>

Without this, the two writes can drift apart. Create the chain before saving the user and a failed save leaves an email going to nobody; save first and a crash before `createChain` leaves a user who never gets an email. Passing the same `txCtx` to your own write and to `client.createChain` makes them one unit. The in-process state adapter opens the transaction with `withTransaction`, rolls back when the callback throws, and can run your own code on rollback with `onTransactionRollback`, which the lesson uses to undo a write to an in-memory map. A database provider does this for real rows.

A worker only ever sees committed jobs. Queuert reports the new chain after the commit, so a rolled-back chain never reaches a worker, and the output shows the sign-up rolled back with no user saved.

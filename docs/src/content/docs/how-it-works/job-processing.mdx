An attempt is one run of a job's handler. Queuert opens no transaction around it: the handler does its work, then opens its own transaction and ends the attempt with `applyJobOutcome` inside it. Ownership of the job is enforced by conditional writes, not by a lock held for the attempt.

## Transactional design

Jobs are created inside the same transaction as your application state, the transactional outbox pattern. If the transaction rolls back, the job is never created, and the job always references state that exists. The [Chains in your transaction](/queuert/learn/chains-in-your-transaction/) lesson shows the call; the [dual-write problem](../../blog/dual-write-problem/) post explains what it replaces.

The same holds at the other end. The handler does its reads, external API calls and long computations first, then opens a transaction, writes its domain changes and calls `applyJobOutcome` in it. The outcome (an output that completes the chain, a `continueWith` that adds the next job, or a reschedule) commits or rolls back together with those writes:

```typescript
attemptHandler: async ({ job, applyJobOutcome }) => {
  const { paymentId } = await paymentAPI.charge(job.input.amount);

  await withTxHooks(async (txHooks) =>
    db.transaction(async (tx) => {
      await tx.orders.update({ where: { id: job.input.orderId }, data: { paymentId } });
      return applyJobOutcome({ tx, txHooks, output: { paymentId } });
    }),
  );
},
```

`applyJobOutcome` registers its observability events and notifications through the state provider's `onTransactionCommit`, so they are released only after your transaction commits. If it rolls back, none of them is sent, apart from a wake-up for the pending jobs your transaction locked; see [Tx hooks](../../guides/tx-hooks/).

1. **Acquire.** The worker starts an attempt under its id, which it holds while the worker's lease is live; see [Worker runner](../worker-runner/#worker-lease).
2. **Handler.** Your handler does its work, then opens a transaction and calls `applyJobOutcome` in it.
3. **Commit detection.** The worker records the attempt as completed if the commit callbacks of an `applyJobOutcome` call ran, and otherwise fails it; see [Errors and commit detection](#errors-and-commit-detection).

## `applyJobOutcome`

`applyJobOutcome` ends the attempt. Whether the job ends up completed depends on the outcome you pass. It takes your transaction context spread alongside exactly one outcome — the same convention as `client.createChain`:

- `applyJobOutcome({ ...txCtx, output })` — completes the job and its chain, and unblocks jobs waiting on the chain.
- `applyJobOutcome({ ...txCtx, continueWith: { typeName, input, blockers?, schedule? } })` — completes the job and adds the next job to the chain.
- `applyJobOutcome({ ...txCtx, reschedule: { afterMs } | { at }, reason? })` — returns the job to pending without counting the attempt as failed, setting `consecutiveFailures` to 0 and storing `reason` as `lastRescheduleReason`.

The transaction context is required, including every field the provider's context type requires, such as the `txHooks` of a provider that carries them in its context. `applyJobOutcome` performs several writes (for example completing the chain and unblocking its dependents), so it always needs your transaction. It throws if the state adapter's `getTransaction` reports the context as outside an open transaction, for example when you pass a pool or the root ORM handle. On PostgreSQL it can run at any isolation level, and at REPEATABLE READ or SERIALIZABLE it can fail with a serialization failure that you retry; see [PostgreSQL state adapter](/queuert/integrations/state-adapters/postgres/#isolation-level). On SQLite with an async provider it must hold the provider's write lock; see [SQLite state adapter](/queuert/integrations/state-adapters/sqlite/#asyncrwlock). On MySQL and MariaDB it can run at any isolation level, and can fail with a deadlock, or a snapshot conflict on MariaDB, that you retry; see [MySQL / MariaDB state adapter](/queuert/integrations/state-adapters/mysql/#isolation-level). On Redis it must be the context the adapter's `withTransaction` passed; see [Redis state adapter](/queuert/integrations/state-adapters/redis/#transactions).

**Await the transaction that calls `applyJobOutcome`.** The handler returns nothing: `await withTxHooks(async (txHooks) => db.transaction(async (tx) => applyJobOutcome({ tx, txHooks, output })))`. Whether the attempt completed is decided by [commit detection](#errors-and-commit-detection), and a handler that ends without a committed `applyJobOutcome` fails the attempt.

**With a synchronous state adapter, `applyJobOutcome` is synchronous.** Processors built with `createProcessors` over a client of a [synchronous state adapter](/queuert/integrations/state-adapters/sqlite/#synchronous-providers) give the handler an `applyJobOutcome` that returns the job directly and throws synchronously, so it runs inside the driver's own transaction and an error rolls that transaction back: `withTxHooks((txHooks) => db.transaction(() => applyJobOutcome({ db, txHooks, output }))())`. The handler itself stays `async`; `fenceJob` is synchronous the same way.

**One `applyJobOutcome` per attempt.** A second or concurrent call throws an `Error` before writing anything and leaves the attempt running, whether or not the first one's transaction has committed yet. A call that threw before writing (for example a validation error), or whose transaction or savepoint rolled back, does not count, so you can catch the error and call `applyJobOutcome` again. `applyJobOutcome` cannot be called after the handler has ended.

**Each job of a batch has its own attempt.** A [batched processor](/queuert/guides/batched-processors/) settles the jobs of its batch with its handler's `applyJobOutcomes`, so the rules above hold per job.

## Attempt ownership

Every write tied to an attempt is conditional on the job row: the job must be `running` and still hold the attempt token it was given when this attempt acquired it. Each acquisition gets a new token, so an earlier attempt, or one of a chain deleted and recreated under the same id, never matches. A conditional write that does not match writes nothing at all — no completed job, no chain update, no continuation. This is what makes `applyJobOutcome` safe without Queuert holding a lock for the duration of the attempt.

When its write misses, `applyJobOutcome` writes nothing, throws and aborts `job.signal`; let the error propagate so your transaction rolls back with it.

### `fenceJob`

`applyJobOutcome` checks ownership for its own transaction only. For writes in the other transactions your handler opens, call `fenceJob({ ...txCtx })` at the start of that transaction. It takes the same transaction context as `applyJobOutcome`, with the same SQLite write-lock and Redis requirements, though like a read it needs only part of it: `fenceJob({ tx })` without the `txHooks` some providers carry is enough. It locks the job row and its chain head and checks that the job is `running` under this attempt's token. Reclaiming the job, completing it with `client.applyJobOutcome`, reading it with `lock: "exclusive"` and deleting its chain all lock or update the same rows, so they wait until your transaction commits or rolls back: every write that commits after a successful `fenceJob` committed while the attempt owned the job. On Redis nothing waits: the transaction that commits second runs again, and its `fenceJob` then throws; see [Locks](/queuert/integrations/state-adapters/redis/#locks).

```typescript
attemptHandler: async ({ job, fenceJob, applyJobOutcome }) => {
  for (const batch of batches) {
    if (job.signal.aborted) break;
    await db.transaction(async (tx) => {
      await fenceJob({ tx });
      await writeBatch(tx, batch);
    });
  }
  await withTxHooks(async (txHooks) =>
    db.transaction(async (tx) => applyJobOutcome({ tx, txHooks, output: null })),
  );
},
```

When the attempt no longer owns the job, `fenceJob` throws `JobTakenByAnotherWorkerError`, `JobAlreadyCompletedError` or `JobNotFoundError` and aborts `job.signal`; let it propagate so the transaction rolls back. `fenceJob` writes nothing, so it can be called any number of times. In the transaction that calls `applyJobOutcome`, call it before `applyJobOutcome`: `applyJobOutcome` ends the attempt, so a later `fenceJob` treats it as lost. A batched handler's `fenceJobs({ ...txCtx, jobs })` does the same for the jobs it names, throwing `JobsTakenByAnotherWorkerError`, `JobsAlreadyCompletedError` or `JobsNotFoundError` that list each lost one. While a fenced transaction is open, reclaim, client writes to the chain and new chains that use it as a blocker wait for it, so keep fenced transactions short. On PostgreSQL, a fenced transaction that then locks other chains, for example by deleting them, can deadlock with a client call that locks the same chains in a different order; PostgreSQL aborts one of the two transactions, and a handler that lets the error propagate is rescheduled. Transactions without `fenceJob` are not checked against ownership: their writes can commit after the attempt was lost, so keep them idempotent.

## Errors and commit detection

The attempt counts as completed once a successful `applyJobOutcome` call's commit callbacks run, which the state provider's `onTransactionCommit` does after your transaction commits, so a successful attempt needs no extra database round-trip. If no `applyJobOutcome` call's commit callbacks ran — the handler threw before committing, or returned without calling `applyJobOutcome` — the attempt fails: the worker runs one reschedule under the attempt token, which reschedules the job with backoff while the attempt still owns it and matches nothing if an `applyJobOutcome` committed or the attempt was lost. An error thrown after a committed `applyJobOutcome` does not roll the completion back; it is reported as a `workerError`. For a [batched processor](/queuert/guides/batched-processors/), each job's attempt counts as completed once the commit callbacks of the handler's `applyJobOutcomes` call that names it run.

Commit callbacks stand for a committed write only when the state provider meets these requirements:

- **Commit callbacks run only after COMMIT.** A provider that carries `TxHooks` in its context creates them with `withTxHooks` around the transaction, so they flush after COMMIT; created inside the transaction, they would flush before COMMIT, and a COMMIT that then fails leaves nothing written. When you open the transaction yourself for such a provider, wrap it the same way.
- **Callbacks follow savepoints.** An `applyJobOutcome` inside a database savepoint that rolls back must have its commit callbacks dropped with it. A provider with transaction events does this itself; with `TxHooks` in the context, pair the database savepoint with `txHooks.withSavepoint` (or a `createSavepoint` handle rolled back alongside it) and pass the savepoint's hooks to `applyJobOutcome`. See [Tx hooks](../../guides/tx-hooks/#savepoints).
- **A try the driver reruns drops its callbacks.** When the driver reruns the transaction callback, the rolled-back try's `applyJobOutcome` must not count. With `TxHooks`, wrap the rerun callback in `txHooks.retryBoundary`. See [Tx hooks](../../guides/tx-hooks/#drivers-that-rerun-the-callback).
- **A rolled-back transaction is reported as rolled back.** A knex transaction resolves after a bare `trx.rollback()`, which `withTxHooks` takes for a commit, unless it is given `{ doNotRejectOnRollback: false }`. See [Tx hooks](../../guides/tx-hooks/#a-resolved-transaction-counts-as-committed). MikroORM fires no rollback event when PostgreSQL answers COMMIT with ROLLBACK after a caught statement error, so let statement errors propagate out of `em.transactional`.

If any of them is broken, the worker can count the attempt as completed although nothing was written. The job then stays `running` until the worker is next idle and reclaims it as a failed attempt; see [Worker runner](../worker-runner/#reclaim).

[Job processing reliability](../processing-reliability/) walks through each scenario with code, and [Error handling](../../guides/error-handling/) covers jobs that fail permanently.

## Abort signal

Every job an attempt handler receives carries a `job.signal` that aborts when the worker is stopping, when its worker lost its lease, or when the job's attempt is lost (taken by another worker, deleted, or completed externally). Your own committed outcome never aborts it. On abort, stop working and commit an `applyJobOutcome` — with partial output or `{ reschedule }` — or throw, which fails the attempt: it adds to `consecutiveFailures` and reschedules with backoff. A worker that is only stopping, as on every deploy, is no fault of the job, so a handler that expects it reschedules with `applyJobOutcome({ reschedule })` instead of throwing. If the attempt was lost, `applyJobOutcome` and `fenceJob` write nothing and throw. A handler that returns without a committed `applyJobOutcome` fails the attempt.

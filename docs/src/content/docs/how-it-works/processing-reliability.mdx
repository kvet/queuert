When a handler throws, its transaction rolls back any partial work and the worker reschedules the job with [backoff](/queuert/how-it-works/worker-runner/#retry-and-backoff). Once an `applyJobOutcome` has committed, the outcome stands, wherever the error occurs. The scenarios below show each case; [Error handling](../../guides/error-handling/) covers jobs that fail permanently and [Errors and commit detection](/queuert/how-it-works/job-processing/#errors-and-commit-detection) how the worker tells a committed attempt from a failed one.

## Error before the transaction

Work before your transaction — reads, external API calls — runs without a transaction. If it throws, nothing was written and the job is rescheduled with [backoff](/queuert/how-it-works/worker-runner/#retry-and-backoff).

The next attempt runs the external call again, so make its side effects idempotent: the payment API above receives `job.id` as its idempotency key, so the order is charged once however many attempts run.

## Error inside the transaction

If your transaction callback throws, your database client rolls the transaction back — undoing any SQL you executed, the job completion, and any continuation jobs created via `continueWith` — and the job is rescheduled with backoff. In the example, `updateBalance` stands for an `UPDATE` guarded by a `CHECK (balance >= 0)` constraint: it throws when the balance would go negative, and its earlier writes in the transaction roll back.

<ExampleCode example="guides" file="src/error-recovery.ts" region="inside-transaction" />

While the source account lacks the funds, every attempt credits the target account and then fails on the debit, so both writes roll back and the job keeps being rescheduled. Once the source account is topped up, the next attempt commits the transfer.

The same holds for a throw after `applyJobOutcome` returned but before the transaction commits: the completion is part of your transaction, so it rolls back together with your writes.

## Intermediate transactions

A handler can commit work in its own transactions before the one that calls `applyJobOutcome`. Those transactions are not tied to the attempt unless they call [`fenceJob`](/queuert/how-it-works/job-processing/#fencejob): if an error occurs after one commits (typically a failed external API call), the job is rescheduled with backoff, its side-effects persist, and the next attempt runs it again. Intermediate transactions without `fenceJob` commit even if the attempt is later lost to another worker. Call [`fenceJob`](/queuert/how-it-works/job-processing/#fencejob) at the start of one to commit it only while the attempt owns the job, and design its side-effects to be safe to keep when the job is rescheduled.

## Error after `applyJobOutcome` committed

Once the transaction that called `applyJobOutcome` has committed, the outcome is final. If the handler throws afterwards, the error is reported as a worker error (`workerError`), but the completion is not rolled back and the job is not rescheduled. ## Guarantees

- **Reschedule before the commit.** An error before your transaction or inside it reschedules the job with the [backoff](/queuert/how-it-works/worker-runner/#retry-and-backoff) delay, and so does a handler that returns without a committed `applyJobOutcome`.
- **No partial state.** Your transaction never commits partial SQL work when an error occurs.
- **No orphaned continuations.** When the transaction throws after `applyJobOutcome` was called with `continueWith`, the continuation job and the completion roll back together.
- **Blocked jobs stay blocked.** When a blocker's completion rolls back, its dependents stay blocked.
- **No lost-attempt writes.** `applyJobOutcome` only writes while this attempt still owns the job. If the attempt was reclaimed and another worker took the job, or the job was completed or deleted elsewhere, it writes nothing and throws `JobTakenByAnotherWorkerError`, `JobAlreadyCompletedError` or `JobNotFoundError`, so your transaction rolls back. Writes in your other transactions get the same guarantee when they call [`fenceJob`](/queuert/how-it-works/job-processing/#fencejob) first.
- **No `try/catch` needed.** Let exceptions propagate; the worker handles them.
- **No attempt limit.** A job that keeps failing keeps being rescheduled; [Error handling](../../guides/error-handling/) shows how to end it.

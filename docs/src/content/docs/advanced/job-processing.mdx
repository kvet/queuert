## Overview

This document describes how Queuert processes jobs: the transactional design, how an attempt runs from acquisition to `complete`, and how ownership is enforced without holding locks.

## Transactional Design

Queuert's core design principle is that **jobs are created inside the same database transaction as your application state changes**. This follows the transactional outbox pattern:

```typescript
await withTransactionHooks(async (transactionHooks) =>
  db.transaction(async (tx) => {
    // Application state change
    const image = await tx.images.create({ ... });

    // Job creation in the same transaction
    // The transaction context property name matches your StateProvider
    await client.createChain({
      tx,
      transactionHooks,
      typeName: "process-image",
      input: { imageId: image.id },
    });
  }),
);
```

### Why This Matters

1. **Atomicity**: If the transaction rolls back, the job is never created. No orphaned jobs.
2. **Consistency**: The job always references valid application state.
3. **No dual-write problem**: You don't need to coordinate between your database and a separate job queue.

### Extending to Job Processing

The same principle extends to job processing. Queuert opens no transaction around an attempt: the handler does its work — reads, external API calls, long computations — and then opens its own transaction, writes its domain changes, and calls `complete` inside it. The outcome (an output that completes the chain, a `continueWith` that adds the next job, or a reschedule) commits or rolls back together with those domain writes.

```typescript
attemptHandler: async ({ job, complete }) => {
  const { paymentId } = await paymentAPI.charge(job.input.amount);

  return withTransactionHooks(async (transactionHooks) =>
    db.transaction(async (tx) => {
      await tx.orders.update({ where: { id: job.input.orderId }, data: { paymentId } });
      return complete({ tx, transactionHooks, output: { paymentId } });
    }),
  );
},
```

Observability events and notifications produced by `complete` are buffered in `transactionHooks` and released only after your transaction commits. If it rolls back, nothing leaks out.

1. **Acquire.** The worker starts an attempt and sets its `attemptUntil`.
2. **Heartbeat.** The worker extends the attempt every `attemptConfig.heartbeatMs` until the handler ends or its `complete` commits; see [In-Process Worker](../in-process-worker/#attempt-timeout-and-heartbeat).
3. **Handler.** Your handler does its work, then opens a transaction, calls `complete` in it, and returns the `complete` result.
4. **Commit detection.** The worker records the attempt as completed if a `complete` call's `transactionHooks` flushed, and otherwise fails it; see [Errors and Commit Detection](#errors-and-commit-detection).

## `complete`

`complete` ends the attempt. Whether the job ends up completed depends on the outcome you pass. It takes your transaction context and `transactionHooks` spread alongside exactly one outcome — the same convention as `client.createChain`:

- `complete({ ...txCtx, transactionHooks, output })` — completes the job and its chain, and unblocks jobs waiting on the chain.
- `complete({ ...txCtx, transactionHooks, continueWith: { typeName, input, blockers?, schedule? } })` — completes the job and adds the next job to the chain.
- `complete({ ...txCtx, transactionHooks, reschedule: { afterMs } | { at } })` — returns the job to pending without counting the attempt as failed.

The transaction context and `transactionHooks` are required. `complete` performs several writes (for example completing the chain and unblocking its dependents), so it always needs your transaction. It throws if the state adapter's `isTransaction` reports the context as outside an open transaction, for example when you pass a pool or the root ORM handle. On PostgreSQL, Queuert supports only READ COMMITTED, the default; see [Postgres Internals](../postgres-internals/#isolation-level). On SQLite it must hold the provider's write lock; see [SQLite Internals](../sqlite-internals/#asyncrwlock).

**Return the `complete` result from the handler.** The handler's return type is the finished job, so forgetting `complete` is a compile error. Return it out of your transaction and hooks callbacks: `return withTransactionHooks(async (transactionHooks) => db.transaction(async (tx) => complete({ tx, transactionHooks, output })))`. The type only proves `complete` was called; the worker does not compare the returned value at runtime, and whether the attempt completed is decided by [commit detection](#errors-and-commit-detection).

**One successful `complete` per `transactionHooks`.** A second successful call with the same `transactionHooks` throws, so a loop that retries your transaction must open `withTransactionHooks` inside the loop, once per try. A call that threw before writing (for example a validation error), or one rolled back by `transactionHooks.withSavepoint`, does not count, so you can catch the error and call `complete` again. `complete` cannot be called after the handler has ended.

## Ownership and Fencing

Every write tied to an attempt is conditional on the job row: the job must be `running`, at this attempt number, held by this worker. A conditional write that does not match writes nothing at all — no completed job, no chain update, no continuation. This is what makes `complete` safe without Queuert holding a lock for the duration of the attempt.

When `complete`'s write misses, `complete` writes nothing, throws and aborts the attempt's `signal`; let the error propagate so your transaction rolls back with it.

## Errors and Commit Detection

The attempt counts as completed once the `transactionHooks` of a successful `complete` call flush, so a successful attempt needs no extra database round-trip. If no `complete` call's hooks flushed — the handler threw before committing, or returned without calling `complete` — the attempt fails: the worker runs one reschedule fenced on the attempt, which retries the job with backoff while the attempt still owns it and matches nothing if a `complete` committed or the attempt was lost. An error thrown after a committed `complete` does not roll the completion back; it is reported as a `workerError`.

Flushed hooks stand for a committed write only when two preconditions hold:

- **`withTransactionHooks` wraps your transaction from outside**, so the hooks flush after COMMIT. Opened inside the transaction, they flush before COMMIT, and a COMMIT that then fails leaves nothing written.
- **A `complete` inside a database savepoint that may be rolled back is also wrapped in `transactionHooks.withSavepoint`**, so rolling back the savepoint discards the buffered write too. See [Transaction Hooks](../../guides/transaction-hooks/#savepoints).

If either is broken, the worker can count the attempt as completed although nothing was written. The job then stays `running` until its attempt expires and another worker reclaims it.

See [Job Processing Reliability](../../guides/processing-reliability/) for each scenario with code examples, and [Error Handling](../../guides/error-handling/) for handling permanently failing jobs.

## Abort Signal

Every attempt handler receives a `signal` that aborts when the worker is stopping, when the attempt is lost (taken by another worker, deleted, or completed externally), or when ownership can no longer be confirmed (the heartbeat failed). Your own committed `complete` never aborts it. On abort, stop working and commit a `complete` — with partial output or `{ reschedule }` — or throw to reschedule with backoff. If the attempt was lost, `complete` writes nothing and throws. A handler that returns without a committed `complete` fails the attempt.

```typescript
attemptHandler: async ({ signal, complete }) => {
  let processed = 0;
  for (const item of items) {
    if (signal.aborted) break;
    await processItem(item);
    processed++;
  }
  return withTransactionHooks(async (transactionHooks) =>
    db.transaction(async (tx) => complete({ tx, transactionHooks, output: { processed } })),
  );
},
```

## Overview

This document describes how Queuert processes jobs: the transactional design, how an attempt runs from acquisition to `finish`, how ownership is enforced without holding locks, and how the transaction isolation level you choose affects all of it.

## Transactional Design

Queuert's core design principle is that **jobs are created inside the same database transaction as your application state changes**. This follows the transactional outbox pattern:

```typescript
await withTransactionHooks(async (transactionHooks) =>
  db.transaction(async (tx) => {
    // Application state change
    const image = await tx.images.create({ ... });

    // Job creation in the same transaction
    // The transaction context property name matches your StateProvider
    await client.createChain({
      tx,
      transactionHooks,
      typeName: "process-image",
      input: { imageId: image.id },
    });
  }),
);
```

### Why This Matters

1. **Atomicity**: If the transaction rolls back, the job is never created. No orphaned jobs.
2. **Consistency**: The job always references valid application state.
3. **No dual-write problem**: You don't need to coordinate between your database and a separate job queue.

### Extending to Job Processing

The same principle extends to job processing. Queuert opens no transaction around an attempt: the handler does its work — reads, external API calls, long computations — and then opens its own transaction, writes its domain changes, and calls `finish` inside it. The outcome (an output that completes the chain, a `continueWith` that adds the next job, or a reschedule) commits or rolls back together with those domain writes.

```typescript
attemptHandler: async ({ job, finish }) => {
  const { paymentId } = await paymentAPI.charge(job.input.amount);

  return withTransactionHooks(async (transactionHooks) =>
    db.transaction(async (tx) => {
      await tx.orders.update({ where: { id: job.input.orderId }, data: { paymentId } });
      return finish({ tx, transactionHooks, output: { paymentId } });
    }),
  );
},
```

Observability events and notifications produced by `finish` are buffered in `transactionHooks` and released only after your transaction commits. If it rolls back, nothing leaks out.

1. **Acquire.** The worker picks a pending job and starts an attempt in one autocommit statement: it increments `attempt`, sets `attemptBy` to the worker id and sets the lease `attemptUntil` to now plus the processor's `attemptConfig.timeoutMs`.
2. **Heartbeat.** While the handler runs, the worker renews the lease every `attemptConfig.heartbeatMs`, each renewal a single statement conditional on the attempt still being this worker's. If the worker crashes, the lease lapses and another worker reclaims the job; the crashed attempt counts as used.
3. **Handler.** Your handler runs with no transaction open. It ends by opening a transaction, calling `finish` in it, and returning what `finish` returned.
4. **Post-handler check.** When the handler ends — by returning or by throwing — the worker runs a fenced reschedule. If your `finish` committed, it matches nothing and the attempt is recorded as completed. If no `finish` committed, it reschedules the job with backoff and records the failure.

The worker's own statements (acquire, heartbeat, reclaim, the post-handler reschedule) never run inside your transaction and never open one.

## `finish`

`finish` takes your transaction context and `transactionHooks` spread alongside exactly one outcome — the same convention as `client.createChain`:

- `finish({ ...txCtx, transactionHooks, output })` — completes the job and its chain, and unblocks jobs waiting on the chain.
- `finish({ ...txCtx, transactionHooks, continueWith: { typeName, input, blockers?, schedule? } })` — completes the job and adds the next job to the chain.
- `finish({ ...txCtx, transactionHooks, reschedule: { afterMs } | { at } })` — returns the job to pending without counting the attempt as failed.

The transaction context and `transactionHooks` are required. `finish` performs several writes (for example completing the chain and unblocking its dependents), so it always needs a transaction, and Queuert never opens one for you.

**The handler must return what `finish` returned.** The handler's return type is the finished job, so forgetting `finish` is a compile error. Return it out of your transaction and hooks callbacks: `return withTransactionHooks(async (transactionHooks) => db.transaction(async (tx) => finish({ tx, transactionHooks, output })))`. The type only proves `finish` was called; whether it committed is decided by the post-handler check.

**Validation before writes.** Output parsing, `continueWith` validation and blocker existence checks run before the first write. If `finish` throws, it has written nothing, so catching the error never leaves a partly written chain behind.

**Safe in retried transactions.** If your driver or your own loop retries the transaction callback, `finish` may be called again; the last call wins. `finish` cannot be called after the handler has ended.

### Reading blockers

Job types that declare blockers get `getBlockers` in the handler options. It reads the blocker chains — all completed, in declaration order, typed by the job type definition. Call it without arguments to read on its own connection, or pass your transaction context to read inside that transaction:

```typescript
attemptHandler: async ({ getBlockers, finish }) => {
  const [auth, config] = await getBlockers();

  return withTransactionHooks(async (transactionHooks) =>
    db.transaction(async (tx) =>
      finish({ tx, transactionHooks, output: { userId: auth.output.userId, region: config.output.region } }),
    ),
  );
},
```

Blockers are not preloaded. Acquisition already guarantees all of them are completed, so handlers that only need that guarantee pay no read.

### Long work and intermediate writes

Because no transaction is held while the handler runs, long work — external API calls, file processing, batched database work — needs no special mode. The heartbeat keeps the attempt alive for the whole handler.

If a handler commits intermediate work in transactions of its own before calling `finish` (for example deleting rows in batches), those writes are not tied to the attempt's ownership: they commit even if the attempt is later lost. Make them idempotent, so a later attempt can safely repeat them.

## Ownership and Fencing

Every write tied to an attempt is conditional on the job row: the job must be `running`, at this attempt number, held by this worker. A conditional write that does not match writes nothing at all — no completed job, no chain update, no continuation. This is what makes `finish` safe without Queuert holding a lock for the duration of the attempt.

When `finish`'s write misses, `finish` throws and aborts the attempt's `signal`:

| Situation                                                           | Error                          | `signal.reason`             |
| ------------------------------------------------------------------- | ------------------------------ | --------------------------- |
| The lease lapsed and the job was reclaimed or acquired by another worker | `JobTakenByAnotherWorkerError` | `"taken_by_another_worker"` |
| The job was completed elsewhere, e.g. by `client.completeChain`     | `JobAlreadyCompletedError`     | `"already_completed"`       |
| The job was deleted                                                 | `JobNotFoundError`             | `"not_found"`               |

Let the error propagate: your transaction rolls back and takes your domain writes with it.

Once `finish` has written the job row, your transaction holds that row until it ends: a heartbeat renewal waits for it, and reclaim skips the row, so neither interferes with your commit.

## Errors and Commit Detection

Whether `finish` committed is decided by the database, not by the handler's return value:

- **The handler throws before `finish` commits** (an API call fails, a constraint fires inside your transaction, the transaction fails to commit): your driver rolls the transaction back, and the post-handler check reschedules the job with exponential backoff (default: 10 s → 20 s → 40 s → ... capped at 300 s), recording the error as `lastAttemptError`.
- **The handler returns without a committed `finish`** (for example `finish` ran inside a savepoint you rolled back): the attempt fails with `Attempt handler returned without a committed finish` and is rescheduled with backoff.
- **The handler throws after `finish` committed**: the completion stands. The error is recorded for the attempt, but nothing is rolled back or rescheduled. Work you do after your transaction commits is your responsibility.

There is no maximum retry count — jobs retry indefinitely. Use [discriminated unions or compensation patterns](../../guides/error-handling/) to handle permanently failing jobs. See [Job Processing Reliability](../../guides/processing-reliability/) for scenarios with code examples.

## Isolation Levels

You choose the isolation level of every transaction that touches Queuert state — the one you pass to `finish`, and the ones you pass to `client.createChain` and other client methods. Queuert is correct at READ COMMITTED, REPEATABLE READ and SERIALIZABLE; what differs is whether a conflict waits or fails.

| Situation                                                                                              | READ COMMITTED                                                            | REPEATABLE READ / SERIALIZABLE                                             |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `finish` in a handler while another transaction writes the job row                                     | waits for it, re-checks ownership, and writes nothing if the attempt was lost | serialization error if the job row changed since your transaction's snapshot |
| Client calls that lock and then check a job (`client.completeChain`, `client.rescheduleJobs`)          | waits, then sees the latest row                                           | serialization error if the row changed since the snapshot                  |
| Adding a blocker on a chain (`createChain` or `continueWith` with `blockers`) while that chain completes | waits and re-reads; the dependent job ends up correctly `blocked` or `pending` | serialization error on one of the two sides                                |

Both sides of the blocker race write the blocker chain's head row — completing the chain writes it, and adding a blocker writes it too — so the race is a write conflict at every isolation level and a dependent job is never left `blocked` behind a completed chain.

A serialization error is an ordinary database error:

- **In a handler**, it fails your transaction, and the attempt is rescheduled with backoff. You can also retry the transaction inside the handler; `finish` is safe to call again (last call wins).
- **In client code** (`createChain` with blockers, `completeChain`, ...), retry the transaction, as you must for any transaction at these levels.

When retrying, open a fresh `withTransactionHooks` scope per try, so events buffered by a rolled-back try are discarded with it.

The worker's own statements (acquire, heartbeat, reclaim, the post-handler reschedule) are single autocommit statements, so the session's default isolation level does not change their behaviour.

## SQLite: Hold the Write Lock

SQLite providers share one connection guarded by a process-wide `AsyncRwLock`. The worker's autocommit statements for other attempts run on that connection under the lock. A handler transaction opened **without** the write lock would let those statements run inside it, and rolling it back would undo another attempt's acquisition. Open every transaction you pass to `finish` (or to any client method) while holding the provider's write lock — for example `using _lock = await lock.acquireWrite()` before `BEGIN`, as the provider's own `withTransaction` does. See [SQLite Internals](../sqlite-internals/#asyncrwlock).

## Abort Signal and Reasons

Every attempt handler receives a `signal` (`TypedAbortSignal<JobAbortReason>`) that is aborted when the job should stop. The `signal.reason` distinguishes the cause:

| Reason                      | Meaning                                                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------------- |
| `"taken_by_another_worker"` | The attempt's lease lapsed and the job was reclaimed or acquired by another worker                |
| `"not_found"`               | The job no longer exists in the database                                                          |
| `"already_completed"`       | The job was already completed                                                                     |
| `"error"`                   | Renewing the attempt (heartbeat) failed unexpectedly — ownership is uncertain, not confirmed lost |
| `"worker_stopping"`         | The worker is shutting down — the job is still valid and the attempt is still held                |

The first three reasons indicate the job is no longer owned by this worker, and `"error"` means ownership can no longer be confirmed — in all four cases handlers should stop immediately; a `finish` would fail anyway. Your own committed `finish` never aborts the signal. `"worker_stopping"` is different: the job remains valid, but the worker is draining, so handlers should check `signal.reason` and wrap up quickly. Every attempt must still end in an outcome: commit a `finish` (which may `reschedule`), or throw so the attempt is rescheduled with backoff. A handler that returns without a committed `finish` fails the attempt.

```typescript
attemptHandler: async ({ signal, finish }) => {
  for (const item of items) {
    if (signal.aborted && signal.reason === "worker_stopping") {
      break; // stop early, finish with partial results
    }
    await processItem(item);
  }
  return withTransactionHooks(async (transactionHooks) =>
    db.transaction(async (tx) => finish({ tx, transactionHooks, output: { processed: items.length } })),
  );
},
```

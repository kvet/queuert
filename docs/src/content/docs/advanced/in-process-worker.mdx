## Overview

This document describes the worker design in Queuert: how workers coordinate job processing, manage concurrency, and handle failures.

A **worker** runs a main loop that coordinates job processing across multiple **slots**. Each slot processes one job at a time; the worker manages concurrency and scaling.

## Concurrency Model

Workers process jobs in parallel using slots. See `createInProcessWorker` TSDoc for configuration options. Default: single slot (`concurrency: 1`).

**How it works:**

1. Main loop acquires up to the idle slot count of jobs in one `startJobAttempts` call and spawns a slot per job
2. Each slot processes its job independently
3. When slots complete, main loop acquires a batch for the freed slots
4. Workers compete for jobs via database-level locking (`FOR UPDATE SKIP LOCKED` in PostgreSQL)

## Worker Lifecycle

### Main Loop

The worker runs a single coordinating loop:

1. **Fill**: Call `startJobAttempts` with the idle slot count as `limit`, start each returned job in its own slot, and repeat until a call returns fewer jobs than its `limit` or all slots are busy. Each call is a single autocommit statement that starts up to `limit` attempts and sets each `attemptUntil` to now plus that job type's `attemptConfig.timeoutMs`, so filling `N` idle slots costs one round-trip, and an idle worker issues one acquisition per wake-up
2. **Reclaim expired attempts**: Reclaim up to the idle slot count of jobs with an expired attempt (if any idle slots remain); if any were reclaimed, skip the wait and start the next iteration
3. **Wait**: Listen for notification, poll timeout, or slot completion
4. **Repeat**

If an iteration throws, the worker emits `workerError` and sleeps per `recoveryBackoffConfig` before the next one. The backoff grows only while consecutive iterations keep failing and resets once an iteration completes, so an isolated error long after a past outage gets the initial delay rather than the maximum.

### Shutdown

On startup, the worker emits a `workerStarted` observability event.

Calling `stop()` triggers graceful shutdown:

1. Emit the `workerStopping` observability event
2. Signal abort controller — in-flight jobs see their `signal` abort, and the main loop stops spawning new slots
3. Wait for the main loop to exit, then for all in-flight handlers to end (return or throw)
4. Emit the `workerStopped` observability event

Stopping is cooperative: the attempt is still held, so handlers that check `signal.aborted` can wrap up and still commit a `complete` (with partial output or `{ reschedule }`) instead of abandoning work.

## Worker Identity

Each worker has a unique identity (a random UUID, prefixed with the optional `workerName` option when set) stored in `attemptBy`. The worker tracks active jobs internally and routes abort signals by job ID—no per-slot identity is needed: the worker checks the job's `attempt` as well as `attemptBy` before each write, so a slot whose attempt was reclaimed and re-acquired by another slot of the same worker fails with `JobTakenByAnotherWorkerError`.

## Attempt Timeout and Heartbeat

Every attempt has a deadline, `attemptUntil`, set when the job is acquired from `attemptConfig.timeoutMs`. While the handler runs, the slot extends it every `attemptConfig.heartbeatMs` with a single autocommit statement that only matches while the job is still `running` at this attempt and held by this worker. The heartbeat stops when the handler ends or its `complete` commits. An extension that misses after the attempt's own `complete` wrote simply stops the heartbeat; any other miss means the attempt was lost (another worker took it, it was completed elsewhere, or it was deleted) and aborts the handler's `signal`. An extension that fails with a database error also aborts the `signal` and stops the heartbeat, since ownership cannot be confirmed.

If the worker crashes, nothing extends the attempt; once it expires, a worker reclaims the job. The crashed attempt counts as used.

## Expired Attempt Reclamation

The worker reclaims jobs with expired attempts, making them available for retry.

When idle slots remain in the main loop:

1. Find up to the idle slot count of `running` jobs of registered types whose `attemptUntil` has passed (the exact selection is adapter-specific — e.g. PostgreSQL takes types in random order and the oldest expired jobs within each)
2. Transition the jobs in a single autocommit statement: `running` → `pending`, clear `attemptAt`, `attemptBy`, and `attemptUntil`, and stamp `lastAttemptAt` and `lastAttemptError` (`JobAttemptExpiredError: Job attempt expired before the holding worker extended it`)
3. Emit a `jobAttemptReclaimed` observability event per job
4. Notify via `provideWakeHint` and `notifyJobScheduled` once per job type, with the type's reclaimed count as the hint (workers wake up), and `notifyJobAttemptLost` per job (original worker aborts)

**Design decisions:**

- **Integrated with main loop**: Runs once per iteration, no separate process needed.
- **Bounded by idle slots**: Reclaims at most as many expired attempts as the worker has idle slots, so one iteration never releases more work than it can pick up itself.
- **Type-scoped**: Only reclaims expired attempts for job types the worker is registered to handle.
- **Concurrent-safe**: The reclaim skips rows another transaction holds (`SKIP LOCKED` in PostgreSQL), so it never interferes with a handler transaction that has already written the job in `complete`.
- **Self-aware**: When running with multiple slots, the worker excludes jobs currently being processed by itself (via `ignoredJobIds`). This prevents a race condition where a worker could reclaim its own in-progress job if the attempt expires before the heartbeat extends it.

## Retry and Backoff

When a job handler throws before a `complete` commits, or returns without a committed `complete`, the worker reschedules it with exponential backoff, in a single autocommit statement fenced on the attempt:

```
delay = min(initialDelayMs * multiplier^(attempt-1), maxDelayMs)
```

Example with defaults: 10s → 20s → 40s → 80s → 160s → 300s → 300s...

See [Job Processing](../job-processing/) for details on error handling and abort signals.

`createInProcessWorker` validates every `recoveryBackoffConfig`, `backoffConfig` and `attemptConfig` passed to it, including unused `defaults`, and throws a `TypeError` listing each invalid field. `initialDelayMs` must be finite and non-negative, `maxDelayMs` non-negative (`Infinity` means no cap), and `multiplier`, `timeoutMs` and `heartbeatMs` finite and positive. Fractional values are allowed.

## Client-Based Construction

`createInProcessWorker` accepts a `client` instance and extracts infrastructure (`stateAdapter`, `notifyAdapter`, `observabilityAdapter`, `jobTypes`, `log`) from it internally. Worker-specific options (`processors`, `workerName`, `concurrency`, `pollIntervalMs`, `recoveryBackoffConfig`, `defaults`, `requiredAttemptMiddleware`) remain separate parameters. The top-level `recoveryBackoffConfig` controls the worker's own main loop retry behavior (e.g., recovery from database connection errors). Per-attempt configuration — `backoffConfig`, `attemptConfig`, `attemptMiddleware` — lives on the processor registry; the worker-level `defaults.backoffConfig` / `defaults.attemptConfig` provide a fallback for processors that don't set their own (resolution order: processor → registry → worker `defaults` → library default). `requiredAttemptMiddleware` enforces that every slice merged into the worker includes a fixed set of middleware instances as an in-order subsequence — useful for guaranteeing cross-cutting concerns like auth or tracing are present on every slice. The worker only enforces presence; slices continue to run their own middleware chains.
This is purely a construction convenience — no lifecycle coupling is introduced. The client and worker remain independent after construction.

## Extensibility

### Multi-Type Workers

A single worker can handle multiple job types. The main loop acquires jobs of all registered types for its idle slots, and each slot processes the job it was given. Per-type configuration (attempt, retry) overrides worker defaults.

### Attempt Middlewares

Handler middleware wrap the attempt handler via `wrapHandler`, which can inject typed context into the handler through `next(ctx)` and returns `next`'s result, as its type requires. Middleware compose as an onion: the first middleware's "before" runs outermost. Middleware enable cross-cutting concerns like contextual logging, tracing spans, error classification, and resource injection. See [Job Attempt Middleware](../../guides/middleware/).

Middleware are declared on the processor registry via `createProcessors({ attemptMiddleware: [...] })`. Handler signatures inside that registry auto-infer their typed context from the middleware tuple. When multiple slices are passed as an array to `createInProcessWorker`, each processor keeps its slice's middleware chain. The same holds for registries narrowed with `pickProcessors` / `omitProcessors`. Slices in the array must not share job types: an overlap fails type-checking when the array's length is known at compile time, and throws `DuplicateJobTypeError` at runtime.

To share middleware across multiple registries, list them inline at each `createProcessors` call — the tuple inference narrows without requiring `as const`. Each slice's middleware chain is the runtime source of truth; the worker simply dispatches to whichever processor matches the job's typeName.

## Summary

The worker design emphasizes:

1. **Simplicity**: Single main loop coordinating parallel slots
2. **Efficiency**: Slots are self-contained, main loop just manages concurrency
3. **Reliability**: Integrated attempt reclamation ensures recovery from failures
4. **Flexibility**: Per-type configuration, multi-type workers
5. **Extensibility**: Handler middleware enable cross-cutting concerns

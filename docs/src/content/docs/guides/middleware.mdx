`AttemptMiddleware` wraps an **attempt handler call** — from the moment the worker acquires its jobs until the handler returns. Middleware lets you add cross-cutting logic (tracing spans, contextual loggers, audit trails, shared resources) without touching each individual handler.

  <Flow>
    <Node>worker</Node>
    <Arrow label="acquires jobs" />
    <Group title="middleware · wrapHandler">
      <Flow>
        <Node sub="next(ctx)">before</Node>
        <Arrow />
        <Node>attempt handler</Node>
        <Arrow />
        <Node sub="handler returned or threw">after</Node>
      </Flow>
    </Group>
  </Flow>
</Diagram>

A middleware has a single hook, `wrapHandler`, which wraps the whole attempt handler. It receives the handler call's `jobs` — one job, or every job of the batch for a [batched processor](/queuert/guides/batched-processors/) — and a `next(ctx)` call that yields the inner layer; the object passed to `next` is merged into the handler's options, `attemptHandler` or `batchAttemptHandler`, and its type flows into the handler signature. `next` resolves once the handler returns and rejects with the handler's error; each job's attempt counts as completed once the attempt handler's `applyJobOutcome` or `applyJobOutcomes` call that settles it commits.

See the [`AttemptMiddleware` API reference](/queuert/api/core/type-aliases/attemptmiddleware/) for the full type definition.

## Use cases

### Cross-cutting around the whole handler call

Use for concerns that span the whole handler call: tracing spans, contextual loggers, per-job resources, error classification. `tracing` gives each handler call a trace ID and records a span with its outcome:

<ExampleCode example="guides" file="src/middleware.ts" region="tracing" />

A handler's error propagates through `next()` — the middleware can observe, log, or enrich the error. After the middleware chain unwinds, the engine catches it, fails every job of the call without a committed outcome, and returns normally. Always re-throw the error: swallowing it still fails every job of the call without a committed outcome, but records an "Attempt handler returned without a committed …" error as their `lastAttemptError` in place of the handler's error.

### Load shared data before the handler

Use when you want to load a resource once per handler call and make it available to the handler. `loadTenant` reads the tenant of every job of the handler call before its handler runs and injects `tenantOf`, which returns a job's tenant. The middleware runs outside any transaction, so it reads through your database client directly.

<ExampleCode example="guides" file="src/middleware.ts" region="load-tenant" />

Middleware is not tied to a job type, so `job.input` is `unknown` — narrow it (or validate it) before use.

### Inject helpers used in the handler's transaction

Use to inject helpers that write alongside the handler's `applyJobOutcome` or `applyJobOutcomes` — audit recorders, usage meters. The handler owns the transaction, so the helper takes the transaction context from the handler. `audit` records an event for the job it is given through that transaction:

The handler receives every injected value typed: `traceId`, `tenantOf` and `audit` sit next to `job` and `applyJobOutcome`. It writes the audit event and the invoice in the transaction that calls `applyJobOutcome`:

Because the helper writes through the handler's transaction, its rows commit with the job — and roll back with it if `applyJobOutcome` throws or the transaction fails. In the example the first attempt fails to write the invoice, so its audit event rolls back too, and the next attempt records the event once.

## Composition and order

Middleware is declared on the processor registry, not the worker. Multiple middlewares compose as an onion; the first middleware's "before" runs outermost:

<ExampleCode example="guides" file="src/middleware.ts" region="registries" />

For an `issue-invoice` attempt the order is `tracing` before → `loadTenant` before → `audit` before → handler → `audit` after → `loadTenant` after → `tracing` after. Each `next(ctx)` call accumulates ctx for inner layers. The handler's final ctx is the intersection of all injected ctxs.

## Sharing middleware across registries

To share a common set of middleware across multiple registries (e.g. multiple [slices](/queuert/guides/slices/) merged into one worker), list them inline at each call site, as `billingProcessors` and `notificationProcessors` above do with `tracing` and `loadTenant`. The worker runs both registries:

Per slice, handler ctx types reflect the actual middleware list for that registry — so `audit` is visible in billing handlers but not notification handlers. Inline literals narrow tuple inference automatically; no `as const` is required.

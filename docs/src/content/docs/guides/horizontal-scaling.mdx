## Identical workers

The simplest approach: deploy the same worker configuration on multiple machines or processes.

<ExampleCode example="guides" file="src/horizontal-scaling.ts" region="identical" />

Each worker runner here passes a stable `workerId`, such as a pod name; a process restarting under it waits until the previous registration's lease expires, then reclaims it and starts. Without `workerId`, a worker runner registers under a new id from the state adapter's `generateWorkerId`, a random UUID by default, so processes running the same code never share an id; a restarted process then registers under a new id, and once the lease of its previous registration expires, an idle worker runner reclaims the jobs that registration left behind. Worker runners compete for available jobs — when one acquires a job, others skip it. The notify adapter (PostgreSQL LISTEN/NOTIFY, Redis, etc.) ensures worker runners wake up immediately when new jobs are queued.

## Specialized workers

A worker only processes the job types in its processor registry. This lets you run different worker topologies optimized for different workloads — a worker that doesn't define a processor for a job type simply ignores it. The same mechanism powers [prioritization](../prioritization/): reserve capacity for an urgent workload by giving it a worker of its own.

For CPU-heavy work, run each worker in its own thread or process so they get true parallelism. Each one creates its own client, state adapter and worker — they share nothing except the database. This works because chains are stored in the database, not in worker memory: a chain that starts with `images.resize` (picked up by an image worker) can `continueWith` to `notifications.send-email` (picked up by the default worker) — the handoff happens through the database.

### Splitting a registry

When one `createProcessors` registry (`appProcessors` below) holds the processors for every job type, split it across workers with `pickProcessors` and `omitProcessors`. `pickProcessors` keeps only the listed job types; `omitProcessors` keeps everything else, so the two together cover every job type.

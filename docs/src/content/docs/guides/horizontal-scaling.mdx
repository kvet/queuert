## Identical Workers

The simplest approach: deploy the same worker configuration on multiple machines or processes.

```ts
const worker = await createInProcessWorker({
  client,
  concurrency: 10,
  processors: createProcessors({ client, jobTypes, processors: { ... } }),
});
```

Each in-process worker registers under a new id from the state adapter's `generateWorkerId`, a random UUID by default, so processes running the same code never share an id. A restarted process registers under a new id, and once the lease of its previous run expires, an idle worker reclaims the jobs that run left behind. To keep a stable id per process (a pod name, for example), pass `workerId`; a process restarting under it waits until the previous run's lease expires, then reclaims it and starts. Workers compete for available jobs — when one acquires a job, others skip it. The notify adapter (Redis, PostgreSQL LISTEN/NOTIFY, etc.) ensures workers wake up immediately when new jobs are queued.

## Specialized Workers

A worker only processes the job types in its processor registry. This lets you run different worker topologies optimized for different workloads — a worker that doesn't define a processor for a job type simply ignores it. The same mechanism powers [prioritization](../prioritization/): reserve capacity for an urgent workload by giving it a worker of its own.

For CPU-heavy work, spawn each worker in its own thread so they get true parallelism. Each thread creates its own client, state adapter, and worker — they share nothing except the database:

```ts title="image-worker-thread.ts"
// Each thread runs independently with its own database connection
const stateAdapter = await createPgStateAdapter({ stateProvider });
const client = await createClient({
  stateAdapter,
  notifyAdapter,
  jobTypes: imageJobTypes,
});

const worker = await createInProcessWorker({
  client,
  concurrency: 1,
  processors: createProcessors({
    client,
    jobTypes,
    processors: {
      "images.resize": { attemptHandler: resizeHandler },
      "images.transcode": { attemptHandler: transcodeHandler },
    },
  }),
});
```

```ts title="main.ts"
import { Worker } from "node:worker_threads";

// 10 threads for CPU-heavy image processing
for (let i = 0; i < 10; i++) {
  new Worker("./image-worker-thread.ts");
}

// Lightweight async I/O — single worker in main thread, high concurrency
const notificationWorker = await createInProcessWorker({
  client,
  concurrency: 100,
  processors: createProcessors({
    client,
    jobTypes,
    processors: {
      "notifications.send-email": { attemptHandler: emailHandler },
      "notifications.send-sms": { attemptHandler: smsHandler },
    },
  }),
});
```

This works because chains are stored in the database, not in worker memory. A chain that starts with `images.resize` (picked up by an image worker thread) can `continueWith` to `notifications.send-email` (picked up by the notification worker in the main thread) — the handoff happens through the database.

You can also combine slices when a single worker should handle multiple domains:

```ts
const worker = await createInProcessWorker({
  client,
  processors: [orderProcessors, notificationProcessors],
});
```

See [Feature Slices](../slices/) for organizing job types and processors into independent modules.

### Splitting a Registry

When one `createProcessors` registry (`appProcessors` below) holds the processors for every job type, split it across workers with `pickProcessors` and `omitProcessors`. `pickProcessors` keeps only the listed job types; `omitProcessors` keeps everything else, so the two together cover every job type. Each processor keeps its handler, its slice's middleware chain, and its `backoffConfig`:

```ts
import { omitProcessors, pickProcessors } from "queuert";

const imageJobTypeNames = ["images.resize", "images.transcode"] as const;

const imageWorker = await createInProcessWorker({
  client,
  concurrency: 1,
  processors: pickProcessors(appProcessors, imageJobTypeNames),
});

const defaultWorker = await createInProcessWorker({
  client,
  concurrency: 100,
  processors: omitProcessors(appProcessors, imageJobTypeNames),
});
```

Job type names are type-checked against the registry, and both functions throw on a name the registry has no processor for. Neither accepts a selection that leaves no processors. To pick from several slices, pick from each one and pass the results as an array: `processors: [pickProcessors(orderProcessors, [...]), pickProcessors(billingProcessors, [...])]`.

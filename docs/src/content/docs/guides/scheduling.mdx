## Rescheduling from a Handler

When a handler needs to defer work without treating it as a failure — for example, a rate-limited API saying "come back later" — use `complete({ reschedule })`. The handler below waits as long as the API asks before calling it again:

<ExampleCode example="guides" file="src/scheduling.ts" region="reschedule-from-handler" />

Because `complete({ reschedule })` is a normal outcome — not an error — the job keeps a clean slate: no `lastAttemptError`, no failure event, no error span. The attempt counter still increments, so backoff reflects total attempts if the job later fails for real. `reschedule` takes the same `{ afterMs }` or `{ at }` as `schedule`.

## Rescheduling Pending Jobs

A scheduled job is just a pending job with a future `scheduledAt`. Use `rescheduleJob` (or `rescheduleJobs` for a batch) to change when it runs. Pass `schedule: { at }` or `{ afterMs }` to move it to a different time — here the reminder moves to two hours from now:

`rescheduleJob` throws `JobNotFoundError` if the job does not exist and `JobNotReschedulableError` if it is not `pending` (blocked, running or completed).

`rescheduleJobs` validates atomically — if any id in the batch is missing or not pending, the entire call fails and no job is rescheduled. Both methods are mutating and require a transaction context.

## Recurring Jobs

Queuert has no cron syntax. For periodic tasks like daily digests, health checks, or billing cycles, start a new independent chain from within the handler instead of using `continueWith`. This keeps each execution as its own short-lived chain rather than building an ever-growing chain history. Each occurrence is its own chain, so the next digest can be pushed back or run now with `rescheduleJob` like any other scheduled job. To make sure only one occurrence is ever queued, add a deduplication key and keep `complete` ahead of `createChain`, as [Self-Scheduling Recurring Chains](../deduplication/#self-scheduling-recurring-chains) explains.

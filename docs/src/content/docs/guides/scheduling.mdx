## Rescheduling from a handler

When a handler needs to defer work without treating it as a failure — for example, a rate-limited API saying "come back later" — use `applyJobOutcome({ reschedule })`. The handler below waits as long as the API asks before calling it again, and says why in `reason`:

<ExampleCode example="guides" file="src/scheduling.ts" region="reschedule-from-handler" />

`applyJobOutcome({ reschedule })` is a normal outcome, not an error: no failure event, no error span. It sets `consecutiveFailures` to 0, so if the job later fails for real, backoff starts again from its initial delay. The optional `reason` is stored on the job as `lastRescheduleReason`, where the next attempt and the dashboard can read it; keep it short, since longer reasons are truncated to 10,000 characters. `reschedule` takes the same `{ afterMs }` or `{ at }` as `schedule`.

## Rescheduling from outside a handler

A scheduled job is just a pending job with a future `scheduledAt`. Use `client.applyJobOutcome` with a `reschedule` outcome to change when it runs. Pass `{ at }` or `{ afterMs }`, and optionally a `reason` — here the reminder moves to two hours from now. Pass `{ afterMs: 0 }` to run it immediately — useful for admin "run now" actions or manually advancing a queued reminder. Past times clamp to now, matching `createChain`. An admin action can find the job a worker has just started, or a chain that has moved on, so it reads the chain's current job with a [locked read](../queries/#locked-reads) and reschedules it only if it is waiting:

<ExampleCode example="guides" file="src/scheduling.ts" region="run-now" />

On a pending or blocked job, a client reschedule works like a handler reschedule: it sets `consecutiveFailures` to 0, restarting backoff, and sets `lastRescheduleReason` to its `reason`, or `null` without one. It keeps `lastAttemptError`, so a job run again by hand still shows why it last failed. A blocked job keeps its status: its `scheduledAt` moves, and it runs no earlier than that once its blockers complete. A running job returns to pending and its attempt is lost, and a completed job throws `JobAlreadyCompletedError`. A blocked job that runs now still waits for its blockers. `applyJobOutcomes` reschedules a batch all or nothing, and also takes the other outcomes, as [Workerless outcomes](../workerless-outcomes/#how-it-works) explains.

## Recurring jobs

Queuert has no cron syntax. For periodic tasks like daily digests, health checks, or billing cycles, start a new independent chain from within the handler instead of using `continueWith`. This keeps each execution as its own short-lived chain rather than building an ever-growing chain history. Each occurrence is its own chain, so the next digest can be pushed back or run now with the client's `applyJobOutcome` like any other scheduled job. To make sure only one occurrence is ever queued, add a deduplication key and keep the handler's `applyJobOutcome` ahead of `createChain`, as [Self-scheduling recurring chains](../deduplication/#self-scheduling-recurring-chains) explains.

Without cleanup, the job table grows unboundedly as completed chains accumulate. This guide shows how to implement cleanup as a regular Queuert job — listing completed chains older than a cutoff date, deleting them in batches using cursor pagination, and scheduling the next run.

<ExampleCode example="guides" file="src/cleanup.ts" region="processor" />

The example sets `CLEANUP_RETENTION_MS` to `0`, `CLEANUP_BATCH_SIZE` to `2` and `CLEANUP_INTERVAL_MS` to one minute so it finishes in a moment; a production deployment keeps chains for days, deletes around 100 chains per batch and runs hourly.

Key patterns used:

- **Retention cutoff** — `CLEANUP_RETENTION_MS` controls how long completed chains are kept before deletion
- **Per-type iteration** — iterates over all chain type names so each type's completed chains are cleaned up independently
- **Status-filtered listing** — `status: "completed"` with `orderBy: "completedAt"` pushes filtering to the database and orders by completion time, so the oldest-completed chains are deleted first
- **Non-blocking chains only** — `blocking: false` skips chains that a job still references as a blocker, which [`deleteChains` rejects](../chain-deletion/#blocker-safety)
- **Cursor pagination** — processes chains in bounded batches using `listChains` cursor, preventing unbounded memory usage
- **Stabilization loop** — repeats the full pass until a round deletes zero chains, so chains that stop blocking after their dependents are removed get cleaned up in subsequent rounds
- **Batched transactions** — each batch of deletions runs in its own short transaction, so the handler never holds a single long-lived transaction
- **Fenced batches** — `fenceJob` at the start of each batch transaction keeps the attempt's ownership until that batch commits, so once the attempt is lost its next batch throws before deleting anything; see [`fenceJob`](/queuert/how-it-works/job-processing/#fencejob)
- **Graceful shutdown** — checks `job.signal.aborted` before each batch; when the worker is stopping, reschedules the job immediately so a fresh worker can resume cleanup
- **`deduplication`** with `scope: "running"` — ensures only one cleanup chain is active at a time
- **Complete before scheduling** — `applyJobOutcome({ output: null })` applies the completion inside the same transaction, so the next run is created against an already-completed chain and does not deduplicate against the one finishing
- **`schedule`** — defers the next run by `CLEANUP_INTERVAL_MS`

## Customization ideas

Since this is your own job type, you can adapt the logic freely:

- **Per-type retention** — filter by `typeName` and apply different cutoff dates
- **Archive instead of delete** — copy chain data to an archive table before deleting
- **Metrics** — emit the number of deleted chains to your observability system
- **Alerting** — when the deletion count exceeds a threshold, throw from the handler so the attempt is rescheduled, or emit an alert

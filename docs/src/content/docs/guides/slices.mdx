As your application grows, defining all job types and processors in a single file becomes unwieldy. Feature slices let you split them by domain — each slice owns its type definitions and processor handlers, composed together at the application level.

## Composing slices

At the application level, pass an array of slices to `createClient`:

<ExampleCode example="guides-slices" file="src/client.ts" />

and an array of their processors to `createWorkerRunner`:

<ExampleCode example="guides-slices" file="src/index.ts" region="worker" />

Both fields accept a single slice or an array of slices. When an array is passed, duplicate type/processor keys are detected:

- **`createClient` / `jobTypes`** — overlapping type names produce a TypeScript error at compile time; validated registries with overlapping `getTypeNames()` throw `DuplicateJobTypeError` at runtime.
- **`createWorkerRunner` / `processors`** — overlapping processor keys produce a TypeScript error at compile time and throw `DuplicateJobTypeError` at runtime.

To run a slice's job types on different workers, split its registry with `pickProcessors` / `omitProcessors` — see [Splitting a Registry](../horizontal-scaling/#splitting-a-registry).

## Cross-slice references

When a slice needs to reference job types from another slice — here, `orders.confirm-order` waits for a notification from the notifications slice — use the optional `TExternal` type parameter on `defineJobTypes`:

<ExampleCode example="guides-slices" file="src/slice-orders-definitions.ts" />

- The first parameter, `T`, holds the owned definitions, which become the registry's phantom type
- The second parameter, `TExternal`, is the read-only reference context and defaults to `Record<never, never>`
- `blockers` validates against entry types in `T & TExternal`
- The registry's phantom type remains `T` only — `TExternal` types are not included

This eliminates the need for "workflow slices" that duplicate type definitions just to make blocker references type-check. When slices are passed as an array to `createClient`, all references resolve against the full set of definitions.

Processors that reference types from another slice need nothing special: the client already exposes every slice's types, so `orders.place-order` creates a `notifications.send-notification` chain and passes it as the blocker of its continuation, and `orders.confirm-order` reads the notification's typed output from `job.blockers`:

## Naming convention

<Aside type="note">
  Prefix job type names with the slice name to avoid collisions and make logs and dashboards easy
  to scan by feature.
</Aside>

```
orders.place-order
orders.confirm-order
notifications.send-notification
```

The runnable code is in [examples/guides-slices](https://github.com/kvet/queuert/tree/main/examples/guides-slices/src). Related: [Chain patterns](../chain-patterns/) for continuation patterns and the [API reference](/queuert/api/core/readme/) for `defineJobTypes`, `createJobTypes`, `createProcessors`, `pickProcessors` and `omitProcessors`.

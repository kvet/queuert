Queuert has no built-in "failure" state, only job completion, so you choose how errors are represented in your job outputs. There is no dead-letter queue either: a job that keeps throwing keeps being rescheduled, with its last error in [`lastAttemptError`](#lastattempterror).

## Rescheduling

A job that throws is rescheduled with backoff, which other queues call a retry; the [Worker runner](/queuert/how-it-works/worker-runner/#retry-and-backoff) owns the delay formula and `backoffConfig`. `fetch-exchange-rate` lets the rate provider's error propagate, and a worker runs a new attempt after the delay:

## lastAttemptError

When the last attempt failed, `job.lastAttemptError` contains its serialized error and `job.consecutiveFailures` is above 0. It is `null` on the first attempt and after an attempt that ended without failing, such as a handler's `applyJobOutcome({ reschedule })`. The client's `applyJobOutcome` with `reschedule` runs no attempt, so it leaves the error in place. The handler above records each error; use it for logging or to adjust how the next attempt behaves. When the previous attempt was reclaimed because its worker lost its lease, stopped, or no longer ran it, it holds a serialized `JobAttemptReclaimedError`.

| Thrown value   | Stored as                                                                   |
| -------------- | --------------------------------------------------------------------------- |
| `Error` object | Stack trace (includes message). Own enumerable properties appended as JSON. |
| Plain object   | JSON-stringified                                                            |
| String         | Stored as-is                                                                |

Values are truncated to 10,000 characters.

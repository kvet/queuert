Queuert provides only job completion — there is no built-in "failure" state. This is intentional: you control how errors are represented in your job outputs. There is no dead-letter queue either: a job that keeps throwing keeps being rescheduled, with its last error in [`lastAttemptError`](#lastattempterror).

## Rescheduling

When a job throws an error, the job is rescheduled with exponential backoff; this is what other queues call a retry. The delay grows with `consecutiveFailures`, the number of attempts in a row that failed, so a job that rescheduled itself on purpose starts again from the initial delay when it later fails. `fetch-exchange-rate` lets the rate provider's error propagate, and a worker runs a new attempt after the delay its `backoffConfig` sets:

## lastAttemptError

When the last attempt failed, `job.lastAttemptError` contains its serialized error and `job.consecutiveFailures` is above 0. It is `null` on the first attempt and after an attempt that ended without failing, such as a handler's `applyJobOutcome({ reschedule })`. The client's `applyJobOutcome` with `reschedule` runs no attempt, so it leaves the error in place. The handler above records each error; use it for logging or to adjust how the next attempt behaves. When the previous attempt was reclaimed because its worker lost its lease, stopped, or no longer ran it, it holds a serialized `JobAttemptReclaimedError`.

| Thrown value   | Stored as                                                                   |
| -------------- | --------------------------------------------------------------------------- |
| `Error` object | Stack trace (includes message). Own enumerable properties appended as JSON. |
| Plain object   | JSON-stringified                                                            |
| String         | Stored as-is                                                                |

Values are truncated to 10,000 characters.

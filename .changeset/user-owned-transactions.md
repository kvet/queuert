Job processing now runs in your own transaction. Queuert no longer opens transactions around an attempt: the handler does its work, opens a transaction with your database client, calls `finish({ ...txCtx, transactionHooks, output | continueWith | reschedule })` inside it, and returns what `finish` returned, so the outcome commits or rolls back together with your domain writes. The worker's own bookkeeping (acquire, heartbeat, reclaim, rescheduling a failed attempt) runs as single autocommit statements conditional on the attempt still owning the job, and every attempt holds a lease from acquisition that the heartbeat renews until the handler ends.

- `prepare`, `step`, `complete`, the atomic and staged processing modes and auto-setup are removed, along with the `AttemptPrepare*`, `AttemptStep` and `AttemptComplete*` types; migrate `complete(async ({ finish, transactionHooks, ...txCtx }) => finish({ output }))` to `withTransactionHooks(async (transactionHooks) => db.transaction(async (tx) => finish({ tx, transactionHooks, output })))`, move `prepare` reads before or into that transaction, and move `step` work into your own separate transactions, which are not tied to the attempt's ownership and must be idempotent.
- `finish` takes one options object with the transaction context and `transactionHooks` (both required) plus exactly one outcome: `{ output }` completes the chain, `{ continueWith: { typeName, input, ... } }` adds the next job, `{ reschedule: { afterMs } | { at } }` returns the job to pending without counting a failure (no `lastAttemptError`, no `jobAttemptFailed`, attempt span `OK`). It writes nothing if the attempt no longer owns the job and throws `JobTakenByAnotherWorkerError`, `JobAlreadyCompletedError` or `JobNotFoundError`, and it is safe to call again in a retried transaction (the last call wins).
- The top-level `rescheduleJob()` helper exported from `queuert` and `RescheduleJobError` are removed (`client.rescheduleJob` and `client.rescheduleJobs` stay); use `finish({ reschedule })` instead.
- `job.blockers` is removed; job types with blockers receive `getBlockers(txCtx?)`, which reads the completed blocker chains on demand, optionally inside your transaction.
- A handler that returns without a committed `finish` fails the attempt and is rescheduled with backoff, and an error thrown after a committed `finish` is recorded but no longer rolls the completion back.
- A crash now always consumes the attempt and is recovered by reclaim once the lease expires; a reclaimed job gets `lastAttemptAt` and a `JobAttemptExpiredError: …` `lastAttemptError`.
- Ownership checks now include the attempt number, fixing a worker with `concurrency > 1` that could re-acquire a job it had lost and finish it from the stale slot.
- Adding a blocker on a chain now writes the blocker chain's head row instead of only locking it, fixing a race under REPEATABLE READ and SERIALIZABLE where a dependent job could stay `blocked` behind a chain that completed concurrently; at those isolation levels the race now surfaces as a serialization error that you must retry, in handlers (where an unretried one fails the attempt and reschedules it with backoff) and in `createChain`/`createChains` with blockers alike.
- On SQLite, every transaction you pass to `finish` must be opened while holding the provider's `AsyncRwLock` write lock, as the provider's own `withTransaction` does.
- `AttemptMiddleware` keeps only `wrapHandler`, which must return what `next` returned; `wrapPrepare`, `wrapStep`, `wrapComplete` and their merged ctx types are removed, and the middleware, `AttemptHandler` and `InProcessWorkerProcessor` type parameters shrink accordingly.
- Each attempt is a single span: the `prepare`, `step` and `complete` child spans, the `queuert.step.index` attribute and `JobAttemptSpanHandle.startPrepare`/`startStep`/`startComplete` are removed, and the attempt span no longer sets `queuert.attempt.result` (read the span status instead).
- The CONSUMER span emitted when a blocker chain completes is renamed from `resolve chain.{type}` to `complete chain.{type}`, and the `queuert.job.completed` metric no longer carries `queuert.worker.id` (use `queuert.job.attempt.completed` for per-worker breakdowns).
- `client.completeChain`'s `complete` option is renamed `handler` and the function it receives is renamed `completeJob`, which uses the same `finish` vocabulary and returns the continuation when the callback returns a `finish({ continueWith })` result.
- `StateAdapter` contract (custom adapters): `withSavepoint` is removed from adapters and state providers, `hasBlockers` from `startJobAttempt` results and `hasBlockedJobs` from `completeJobs` results; `startJobAttempt` takes `timeoutMsByTypeName` instead of `typeNames` and sets the lease; `extendJobAttempt` takes a `fence: { attempt, workerId }`; `completeJobs`, `continueJobs` and `rescheduleJobs` accept a per-job `fence` and must write all or nothing; `reclaimExpiredJobAttempt` takes the `lastAttemptError` to stamp; `getChains` gains `lock: "write"`; `completeJobs` no longer requires a pre-locked head; and the worker-owned methods accept an optional `txCtx` for autocommit. `InProcessContext` now has required fields (`{ inTransaction: true; journal }`).
